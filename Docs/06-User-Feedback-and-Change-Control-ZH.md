# 《废土移动城市》用户反馈与变更控制

> 建立日期：2026-08-04
> 最近更新：2026-08-04
> 当前版本：v1.0
> GitHub 更新方式：每次新增记录或状态变化后，单独提交并推送当前开发分支

## 1. 开发前必读

所有人类开发者和 AI 开发代理在分析、设计、计划、编码、测试或修改文档前，必须先阅读本文件。

本文件统一用于：

1. 反馈测试或试玩中发现的 Bug；
2. 登记用户提出的新构思；
3. 申请改变主 GDD、正式路线图或其他原有文档；
4. 标记每项内容是否已经批准、是否已经实现、是否完成验证。

核心规则：

> 登记不等于批准，批准不等于实现，实现不等于验证。

用户输入先登记，再由用户明确确认是否生效。尚未批准的内容不得修改正式文档、扩大开发范围或进入代码实现。

## 2. 权威边界

- 已运行代码、自动化测试和构建结果代表当前已经实现的事实；
- 主 GDD 代表正式版产品与系统目标；
- 正式路线图代表已批准功能的实现顺序；
- 本文件代表用户最新反馈、审批决策、实现进度和验证证据；
- `已批准` 的文档变更必须先同步到对应正式文档，并在两处建立双向引用；
- 本文件中的计划、讨论或批准内容不得被描述成已经实现。

## 3. 状态定义

### 3.1 审批状态

| 状态 | 含义 | 是否允许开发 |
|---|---|---|
| `待确认` | 已登记，等待用户决定 | 否 |
| `已批准` | 用户明确同意进入正式流程 | 是 |
| `已拒绝` | 用户决定不采用 | 否 |
| `已撤回` | 用户取消此前的请求 | 否 |

### 3.2 实现状态

| 状态 | 含义 |
|---|---|
| `未实现` | 尚未开始修改代码或正式文档 |
| `开发中` | 正在设计、计划或实施 |
| `已实现待验证` | 修改已完成，但尚未满足全部验收条件 |
| `已验证` | 已有对应提交及测试、构建或人工验收证据 |
| `不适用` | 仅作澄清或决策，无需产生实现 |

新记录默认状态必须是：

```text
审批状态：待确认
实现状态：未实现
```

禁止直接从 `未实现` 跳到 `已验证` 而不填写实现提交和验证证据。

## 4. 稳定编号与优先级

### 4.1 稳定编号

- 测试 Bug：`BUG-0001`
- 新构思：`IDEA-0001`
- 文档变更：`DOC-0001`

三类编号分别单调递增。已关闭、拒绝或撤回的编号永久保留，不得复用。

### 4.2 优先级

| 优先级 | 使用条件 |
|---|---|
| `P0` | 无法启动、崩溃、坏档、核心流程无法继续 |
| `P1` | 核心玩法错误、严重数值或交互问题 |
| `P2` | 普通功能、表现、易用性或文档问题 |
| `P3` | 优化建议、远期构思或低影响调整 |

优先级不替代审批。即使是 `P0` 新需求，也必须由用户确认范围；可复现的故障允许先诊断，但修复仍应记录验收条件。

## 10. 标准更新流程

### 10.1 新增反馈

1. 保留用户原始意图；
2. 分配下一个未使用的稳定编号；
3. 在当前待处理总表增加一行；
4. 在对应类型章节增加详细记录；
5. 默认标记为 `待确认 + 未实现`；
6. 提交并推送当前开发分支。

### 10.2 用户批准或拒绝

1. 更新审批状态和最近更新时间；
2. 填写决策原因；
3. 若为 `已批准`，补齐验收条件和影响范围；
4. 若改变原文档，先修改原文档并建立双向引用；
5. 单独提交并推送。

### 10.3 开发与验证

1. 开始设计或实现时标记为 `开发中`；
2. 实现提交完成后标记为 `已实现待验证`，填写提交哈希；
3. 通过规定测试、构建或人工验收后标记为 `已验证`；
4. 填写验证命令、结果或人工验收日期；
5. 将已验证记录移入已关闭记录；
6. 单独提交并推送。

## 11. GitHub 同步规则

这里的“实时更新”指：每次用户明确新增反馈或改变状态后，在同一工作流程内完成文档修改、Git 提交和 GitHub 推送。

- 每次新增记录、批准、拒绝、撤回、开始开发、实现完成或验证完成都应独立提交；
- 使用普通推送，不使用强制推送；
- 未经用户明确授权，不合并默认分支、不创建公开 Release；
- GitHub 暂时不可用时先本地提交，恢复连接后按原顺序推送；
- 不为补写记录而改写已经推送的历史；
- 不提交账号凭据、Unity 许可证、本机缓存、临时构建或机器专用绝对路径；
- 提交前必须确认暂存区只包含本次记录和相关正式文档。

## 12. 每次开发的回写要求

开发者完成任务前必须检查：

- 是否引用了相关 `BUG-`、`IDEA-` 或 `DOC-` 编号；
- 审批状态是否允许当前开发；
- 实现状态是否与真实完成度一致；
- 是否填写实现提交；
- 是否填写验证证据；
- 是否同步修改受影响的主 GDD 或路线图；
- 是否已将补充文档更新推送到 GitHub。
