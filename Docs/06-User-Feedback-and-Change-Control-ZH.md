## 1. 开发前必读

所有人类开发者和 AI 开发代理在分析、设计、计划、编码、测试或修改文档前，必须先阅读本文件。

本文件统一用于：

1. 反馈测试或试玩中发现的 Bug；
2. 登记用户提出的新构思；
3. 申请改变主 GDD、正式路线图或其他原有文档；
4. 标记每项内容的需求是否已经明确、是否已经批准、是否已经实现、是否完成验证。

核心规则：

> 需求明确不等于批准，批准不等于实现，实现不等于验证。

用户提出 Bug、新构思或文档修改后，必须先通过对话澄清修改位置、目标规则、版本边界和验收方式。澄清期间不得直接写入本文件。开发者应先向用户展示需求摘要与原文差异；只有用户确认摘要后，才能登记记录、更新正式文档或改变审批状态。尚未批准的内容不得扩大开发范围或进入代码实现。

## 2. 权威边界

- 已运行代码、自动化测试和构建结果代表当前已经实现的事实；
- 主 GDD 代表正式版产品与系统目标；
- 正式路线图代表已批准功能的实现顺序；
- 本文件代表用户最新反馈、审批决策、实现进度和验证证据；
- `已批准` 的文档变更必须先同步到对应正式文档，并在两处建立双向引用；
- 本文件中的计划、讨论或批准内容不得被描述成已经实现。

## 3. 状态定义

### 3.1 需求明确状态

| 状态 | 含义 | 是否允许申请批准 |
|---|---|---|
| `待澄清` | 仅有原始反馈，修改位置、目标行为或验收边界尚不完整 | 否 |
| `澄清中` | 正在与用户逐项对齐，尚未形成最终摘要 | 否 |
| `已明确` | 用户已确认需求摘要、原文差异、版本边界和修改方式 | 是 |

需求明确状态只描述“要做什么是否说清楚”，不代表用户已经批准开发，也不代表功能已经实现。

### 3.2 审批状态

| 状态 | 含义 | 是否允许开发 |
|---|---|---|
| `待确认` | 已登记，等待用户决定 | 否 |
| `已批准` | 用户明确同意进入正式流程 | 是 |
| `已拒绝` | 用户决定不采用 | 否 |
| `已撤回` | 用户取消此前的请求 | 否 |

### 3.3 实现状态

| 状态 | 含义 |
|---|---|
| `未实现` | 正式需求可以已经同步，但尚未开始代码、美术或运行时实现 |
| `开发中` | 正在设计、计划或实施 |
| `已实现待验证` | 修改已完成，但尚未满足全部验收条件 |
| `已验证` | 已有对应提交及测试、构建或人工验收证据 |
| `不适用` | 仅作澄清或决策，无需产生实现 |

新记录默认状态必须是：

```text
需求明确状态：待澄清
审批状态：待确认
实现状态：未实现
```

禁止直接从 `未实现` 跳到 `已验证` 而不填写实现提交和验证证据。

## 4. 稳定编号与优先级

### 4.1 稳定编号

- 测试 Bug：`BUG-0001`
- 新构思：`IDEA-0001`
- 文档变更：`DOC-0001`

三类编号分别单调递增。已关闭、拒绝或撤回的编号永久保留，不得复用。

### 4.2 优先级

| 优先级 | 使用条件 |
|---|---|
| `P0` | 无法启动、崩溃、坏档、核心流程无法继续 |
| `P1` | 核心玩法错误、严重数值或交互问题 |
| `P2` | 普通功能、表现、易用性或文档问题 |
| `P3` | 优化建议、远期构思或低影响调整 |

优先级不替代审批。即使是 `P0` 新需求，也必须由用户确认范围；可复现的故障允许先诊断，但修复仍应记录验收条件。

### BUG-0001：建造菜单不显示可建造内容

- 提出日期：2026-08-04
- 最近更新：2026-08-05
- 优先级：`P1`
- 需求明确状态：`已明确`
- 审批状态：`已批准`
- 实现状态：`不适用`
- 用户原始描述：建造菜单按下后不显示可建造的东西。
- 运行环境：macOS 15.6，Unity `2022.3.62f1`，`FormalPrototype` 场景 Play 模式。
- 复现步骤：
  1. 在 Unity 中打开 `Assets/_Game/Scenes/FormalPrototype.unity`；
  2. 进入 Play 模式并开始新游戏；
  3. 进入可操作场景后按 `B` 打开建造菜单；
  4. 查看建造菜单是否显示可建造建筑。
- 预期结果：建造菜单清晰显示当前可选择的建筑；已获得线索但条件不足的建筑显示锁定原因；隐藏建筑、尚未接触的路线建筑和唯一特殊建筑不进入普通列表；玩家可以使用键鼠稳定选择。
- 实际结果：按下建造菜单后，没有显示可建造的内容。
- 影响范围：玩家无法确认、选择和放置建筑，阻断基础建造与生产流程。
- 关联正式文档：`Docs/01-Game-Design-Document-ZH.md`、`Docs/05-Formal-Development-Roadmap-ZH.md`、`Docs/superpowers/specs/2026-08-05-3d-building-placement-and-developer-modifier-design.md`
- 关联提交：—（用户决定不修复，因此没有修复提交）
- 验收条件：准确保留原始描述、运行环境和复现事实；明确本问题只属于冻结 2D `FormalPrototype`，决定不修复且没有修复提交；默认 3D 的新建造功能不得计作本问题的修复。
- 验证证据：用户于 2026-08-05 明确批准“不修复冻结 2D 历史问题”的处置；本状态只记录决策，不构成代码修复或问题已解决的证据。
- 决策原因或备注：2D 功能基线已经冻结，默认编辑/构建入口已切换到独立 3D 场景；用户决定不再为冻结 2D 建造菜单追加专属交互。审批状态“已批准”指处置决定已批准，实现状态“不适用”指无需产生实现，不能解释为已修复。新的 3D 建造系统属于 `IDEA-0003` 新功能。

### BUG-0002：默认 3D 场景按 F 后城市没有展开

- 提出日期：2026-08-11
- 最近更新：2026-08-11
- 优先级：`P1`
- 需求明确状态：`已明确`
- 审批状态：`已批准`
- 实现状态：`已实现待验证`
- 用户原始描述：按下 `F` 后没有展开城市。
- 运行环境：macOS，Unity `2022.3.62f1`，默认 `GrayboxPrototype3D` 场景 Play 模式，seed `8128` 的第一版地表运行时接入版本。
- 复现步骤：
  1. 打开 `Assets/_Game/Scenes/GrayboxPrototype3D.unity`；
  2. 进入 Play 模式，保持城市位于默认出生位置；
  3. 按下 `F`；
  4. 观察城市模式、外观和界面反馈。
- 预期结果：默认出生位置必须允许玩家立即完成第一次展开；按 `F` 后城市进入 `Deploying` 并在既定三秒后进入 `Fortress`。玩家后来在不合法地形尝试展开时仍应被规则拒绝，但必须看到明确失败原因。
- 实际结果：原默认出生格覆盖湿地与遗迹，`CityDeploymentRules` 正确拒绝 3×3 展开；输入层又丢弃失败文本，屏幕没有说明，表现为按键无效。实现提交已把 seed `8128` 的默认出生格从 `(8,7)` 移到通过同一规则验证的 `(7,8)`，并把规则返回的失败原因送入现有状态提示区域。
- 影响范围：阻断首次展开、内外城建造验证和后续撤离循环，也让合法性规则缺少必要反馈。
- 关联正式文档：`Docs/01-Game-Design-Document-ZH.md`、`Docs/05-Formal-Development-Roadmap-ZH.md`、`Docs/superpowers/specs/2026-08-05-3d-graybox-foundation-design.md`
- 关联提交：`81df8e8`（默认可展开出生格、部署失败反馈、真实 F 输入回归）。
- 验收条件：正式场景通过真实虚拟键盘主循环验证默认出生位置 `F` 可从 `Mobile` 进入 `Deploying` 并完成为 `Fortress`；不合法地形仍保持 `Mobile`，并显示 `CityDeploymentRules.FailureReason` 对应的可见原因；不得削弱 3×3、阻挡或地形规则。
- 验证证据：RED 证明旧正式场景在真实虚拟键盘 `F` 后仍为 `Mobile`，且失败文本不可见；GREEN 证明默认出生格 `F` 后进入 `Deploying` 并在三秒转换后进入 `Fortress`，无效展开仍只调用一次既有规则并显示其原始失败原因。场景 authoring 连续两次最终字节哈希均为 `e2ef0c372264d261286800fbf71758845cc7819c28357989bb6e9784c5598782`；完整 EditMode `1103/1103`、最终 PlayMode `82/82`、无界面编译通过。尚待用户在实际画面中复验首次展开和提示可读性，因此保持 `已实现待验证`。
- 决策原因或备注：修复默认出生位置与反馈链，不把湿地、遗迹或阻挡地形改成可展开地形，也不复制部署规则。

- 审批状态：`已批准`
- 实现状态：`已实现待验证`

- 运行环境：macOS，Unity `2022.3.62f1`，默认 `GrayboxPrototype3D` 场景 Play 模式，七类正式地表贴图已接入。

### IDEA-0002：领袖倒地、救援、永久死亡与继承

- 提出日期：2026-08-04
- 最近更新：2026-08-04
- 优先级：`P2`
- 需求明确状态：`已明确`
- 审批状态：`已批准`
- 实现状态：`未实现`
- 用户原始描述：领袖可以被救援，但超时后会死亡；领袖只是城市的领袖，死亡后会有新的接班人。
- 设计动机：让领袖成为高价值但可替换的具体角色，使救援、继承人培养、城市忠诚和路线制度形成长期文明风险。
- 目标体验：玩家持续控制文明，并通过当前领袖直接行动；领袖倒地后需要作出救援与城市调度决策，永久死亡造成真实损失但不直接结束游戏。
- 已确认规则：
  - 领袖是玩家当前直接操控的文明角色，不是不可替代的玩家本体；玩家控制权随合法继任者延续；
  - 倒地后进入救援时限，基础时间受伤害、环境、体质、装备、医疗科技和文明路线修正，界面显示剩余时间和主要原因；
  - 可派其他角色接触并持续救治，也可调动移动城市进入范围使用医疗设施更快救援；两种方式都可能被攻击或中断；
  - 成功救援后进入重伤恢复，可能因救援延迟、重复倒地或特殊伤害留下永久伤势；不同路线可通过义体、生物改造、丹药或灵能治疗缓解；
  - 超时后永久死亡，遗体与装备留在现场；可派角色或城市回收，装备可能损坏或被其他势力夺走；
  - 领袖死亡后由临时议会低效维持城市；若长期没有合格继承人，触发紧急选举并产生能力较弱、政治代价更高的临时领袖；
  - 玩家可提前指定并培养独立继承人，但其他高威望、掌军、管理城市或受派系支持的角色也可竞争；
  - 继承方式由文明路线和制度决定。玩家可以强行扶持低支持候选人，但可能引发政变、内战、谈判或政治让步；
  - 预先培养的继承人保留其已有个人成长；紧急产生的新角色从低成长起步。城市、科技和文明进度不会因换领袖清空；
  - 新领袖的路线倾向逐步影响政策、科研和派系，不会瞬间删除既有路线成果；长期改革才可改变文明方向；
  - Demo 保留“重伤暂退、不永久死亡”；完整永久死亡、继承与内部政治在正式路线 F5、且不早于多城市和存档稳定门实现；
  - 意识备份等路线专属能力可以支付代价改变正常死亡与继承流程，但不能绕过统一事件和存档规则。
- 不包含的范围：当前 Demo 不实现永久死亡、继承政治、内战或多候选人界面；不把领袖死亡直接视为文明失败。

### IDEA-0011：3D 生产物流、背包、应急合成、首版科技树与资源状态栏

- 提出日期：2026-08-17
- 最近更新：2026-08-17
- 优先级：`P1`
- 需求明确状态：`已明确`
- 审批状态：`已批准`
- 实现状态：`已实现待验证`
- 用户原始描述：“你自行决定，另外我需要背包，还有科技树，一些材料或者元素，资源状态栏也需要。背包参考异星工厂，科技树你自己决定。资源状态栏参考文明。”本轮同时承接已交接的“生产与物流可观察化”目标，先完成机枪塔之前的生产闭环，不进入敌人、炮塔或战斗开发。
- 设计动机：此前的 3D 主循环已经具备建筑目录、统一放置与施工、资源节点真值、城市状态和物流范围等基础，但尚无可供玩家理解和操作的正式生产闭环。本轮已用背包、受控应急合成、首版科技推进和文明式资源总览补足“获得资源—加工—解锁—观察—调度”的最小玩法循环，最终验证仍待完成。
- 目标体验：玩家能在正式 3D 输入/UI 主循环中观察采矿、冶炼和装配的实时运行状态，通过城市物流或近距离建筑缓存转移资源，在 30 格背包中管理物资并进行有限的应急合成，通过六节点首版科技树解锁前两项实际能力，并从常驻资源栏快速判断库存、容量与净流速。
- 已批准的生产与物流规则：
  1. 采矿站无输入，每 `3` 秒从其绑定节点生产 `1` 单位该节点的真实资源：铁矿节点产出铁矿，能晶节点产出能晶；本轮完整加工链只消费铁矿。冶炼厂每 `6` 秒消耗 `2` 铁矿并生产 `1` 合金；装配厂每 `6` 秒消耗 `2` 合金并生产 `2` 弹药。上述周期是 3D 首版的最终有效周期，不叠加冻结 2D 的要塞生产倍率；数值必须来自正式配置，不得散落硬编码。
  2. 稳定供应关系为 `2 采矿站 → 2 冶炼厂 → 1 装配厂 → 1 座持续射击机枪塔`；本轮只实现和观察机枪塔之前的生产部分。
  3. 每座生产建筑拥有内部输入/输出库存。展开城市提供既有物流范围；范围内建筑通过统一自动物流步骤与城市库存交换资源且不要求相邻，生产周期本身只消费建筑缓存。本条最初批准的“每座仓库为每种资源分别增加 `150`”容量模型已被用户于 2026-08-18 批准的 `IDEA-0012` 替代：仓库改为真实独立的 `150` 共享总容量与可选单资源过滤，具体以 `IDEA-0012` 和当前 GDD 为准。
  4. 建筑离开物流范围后保留内部库存，不能访问城市库存或其他建筑缓存；若本地仍有足够输入和输出空间，可继续运行，直到输入耗尽、输出已满或资源节点枯竭。重新进入范围后恢复既有访问关系。
  5. 资源节点储量与枯竭必须以 `WorldMapModel` 为唯一真值；放置兼容性、城市物流范围和建筑合法性必须复用现有统一规则，不得复制判断或另建影子状态。
  6. UI 必须显示且规则层必须稳定区分五种停工原因：缺少输入、输出已满、不在物流范围、矿脉已枯竭、玩家暂停运行。首版“脱离物流”保持单一状态，不提前拆分电力、维护或通信。
  7. 玩家对单座建筑的运行暂停独立于全局暂停；全局暂停冻结生产、合成和研究时间，不得借此改写建筑自身停工原因。
- 已批准的背包与转移规则：
  1. 玩家会话持有一个 `10×3`、共 `30` 格的背包；每格同种资源最多堆叠 `100`。首版不为背包增加正式存档迁移，schema 保持 `30`。
  2. `E` 打开或关闭统一“背包 + 合成”界面。背包格交互采用左键拿取/放下整堆、右键拆半或逐个放置、`Shift + 左键` 在当前可访问库存之间快速转移；这些背包手势不得与合成次数手势混用。
  3. 背包可与城市库存、当前选中建筑的内部缓存进行显式原子转移。目标容量不足时先计算实际可接收量，并只对该实际量执行一次原子扣除与加入；实际量为零、来源不足或访问条件不满足时不发生转移并显示原因。任一提交步骤失败时完整回滚，不得丢失或复制资源。
  4. 直接访问任意建筑缓存时，建筑必须已完成、归玩家所有且未进入撤离锁定，并且玩家当前直接控制的目标（城市或已招募领袖）距该建筑 footprint 边缘不超过 `2` 格；联网状态不能绕过该距离。脱离物流只表示该近距离人工操作不要求自动物流连接。直接控制城市时始终允许访问该城市库存；直接控制已招募领袖时，领袖距城市核心 footprint 边缘不超过 `2` 格才允许访问城市库存。
- 已批准的应急合成规则：
  1. 只提供两项应急配方：完成“基础冶金”后可用 `4 铁矿 → 1 合金 / 12 秒`；完成“弹药装配”后可用 `4 合金 → 2 弹药 / 12 秒`。配方输入从背包原子预留，产物返回背包。
  2. 合成次数手势为左键加入 `1` 次、右键请求完整加入 `5` 次、`Shift + 左键` 加入当前输入材料与队列余量共同允许的最大次数。右键请求若无法完整承担 `5` 次则整体拒绝，只有 `Shift + 左键` 会自动缩减为最大可承担次数。合成队列按 FIFO 执行，总计最多容纳 `20` 次配方执行；入队时一次性原子预留该批全部输入，不预留输出空间，也不能部分扣除。
  3. 取消尚未完成的项目时 `100%` 返还预留输入；返还空间不足则拒绝取消。产物无可用空间时当前项目阻塞，不丢弃产物，也不跳过到后续项目。
  4. 关闭 `E` 界面后队列继续；统一暂停冻结计时。首版不自动串联合成前置材料，也不扩展为通用手工制造系统。
- 已批准的科技树规则：
  1. 首版按 GDD A16 的六节点建立：`废料加工` 初始已完成；`基础冶金`、`弹药装配` 是本轮仅有的可实际研究节点；`自动防御`、`加固结构`、`遗产解析` 可见但锁定为预览，不可启动。
  2. `基础冶金` 前置为废料加工，消耗 `10` 铁矿、耗时 `20` 秒，解锁冶炼厂机器配方和合金应急合成；`弹药装配` 前置为基础冶金，消耗 `10` 合金、耗时 `30` 秒，解锁装配厂机器配方和弹药应急合成。
  3. 三个预览节点继续显示 A16 数值与依赖：自动防御前置弹药装配，`12` 合金 + `10` 生物质、`35` 秒；加固结构前置自动防御，`20` 合金 + `10` 生物质、`45` 秒；遗产解析前置自动防御，`30` 合金 + `20` 生物质、`60` 秒。它们本轮均不可启动，不提前接入效果。
  4. 开始和推进研究都必须依赖至少一座已完成、归玩家所有且未进入撤离锁定的研究站；失去最后一座合格研究站时暂停但不取消、不退款，恢复后继续。要塞形态研究效率 `100%`，其他城市状态 `50%`。开始研究时从城市库存扣除全部成本；取消返还 `80%` 并清零进度，若完整退款无法原子写回城市库存则拒绝取消；首版不增加研究队列。
  5. 当前代码中的完整 `43` 节点路线不作为本轮运行时科技树。六节点投影复用四个已有 ID：`core.research.automated-machinery`、`core.research.precision-assembly`、`core.research.automated-defense`、`core.research.legacy-analysis`；批准新增仅属于 3D 六节点语义的 `core.research.scrap-processing` 与 `core.research.reinforced-structures`。不得为已有语义再建平行 ID，也不得静默改写四个既有 ID。双资源科技成本必须先进入正式配置模型，不能写成 UI 特例。
- 已批准的资源状态栏规则：
  1. HUD 常驻显示五种基础资源：铁矿、能晶、石料、生物质、水；合金和弹药在首次发现或相应科技解锁后加入常驻栏。以上名称作为本轮正式显示名，由统一资源目录提供。
  2. 每项显示当前数量、容量和净流速；悬停显示收入来源、支出去向、容量来源以及按当前净流速估算的满仓或耗尽时间。无稳定趋势时显示明确的不可估算状态，不伪造时间。
  3. 点击资源栏打开完整资源账本，列出既有全部 `15` 种 `ResourceId`；未发现资源可以保持零值或未知表现，但不得创建新的资源类型或第二套账本真值。
  4. “参考文明”仅指信息层级和快速总览体验，不复制其美术、布局或受版权保护的具体表现。
- 已实现范围：当前分支已经把三条机器配方、建筑内部缓存、城市物流、节点采收与枯竭、仓库容量、脱网本地运行、五类停工原因和单建筑暂停接入正式 3D；`E` 面板提供 30 格背包、城市/建筑缓存原子转移与两条应急合成 FIFO；`T` 面板提供六节点科技投影、两项实际研究、三项锁定预览、研究站资格、模式倍率和取消退款；顶部文明式资源栏显示正式库存、容量、近期净流速、悬停说明和 15 资源账本。上述 UI 已接入真实 Input System 主循环，并与系统菜单、建造和世界输入保持既定优先级。
- 与现有规则的补充或冲突决策：现有研究占位使用单资源成本且存在完整 `43` 节点展示，本轮以 A16 六节点和正式多资源配置为准；现有冻结 2D 对城市状态的研究处理不改动，新 3D 按“要塞 `100%`、其他状态 `50%`”实现。冻结 2D 的 `CityOperationalRules.FortressProductionMultiplier = 1.25` 不进入新 3D 生产，正式 `3/6/6` 秒即有效周期。科技完成关注度运行时不在本轮范围，不提前生效。当前 `BuildingCatalog` 中冶炼厂与研究站施工成本和 GDD A16.2 不一致，本里程碑不静默改动施工成本或冻结 2D 放置体验，作为后续独立变更控制项保留。正式自然开局按 GDD A6.1 初始化，石料为 `0`，但准确 `BuildingCatalog` 中冶炼厂施工仍需 `6` 石料；本轮没有静默修改任一数值。自动生产链测试只用显式开发补给完成 `2 采矿站 → 2 冶炼厂 → 1 装配厂` 的施工，随后清零生产物资再验证自动产出，因此只证明生产运行链，不证明自然开局已经具备石料获取路径。性能门明确为：关闭/静止 UI、非零但不改变显示精度的合成，以及跨真实 fixed step 而内容/revision 不变的稳定生产连续 300 次必须 `0 B`；活跃生产为了保持旧详情快照不可变，只能在固定 `10 Hz` revision 变化时按相关建筑数量线性、有界创建新快照，不能把这一必要分配误写成逐帧零分配，也不得在内容不变时创建候选快照。现有生产、研究和资源 UI 中的占位数据不得被当作正式运行真值；机器配方和应急配方进入同一正式资源配方目录并使用不同稳定 ID，均从科技完成状态派生解锁，不额外保存重复解锁状态。所有新增会话状态均保持会话态，schema 继续为 `30`。

### IDEA-0012：真实仓库库存、单资源过滤、资源图标与精确缺料反馈

- 提出日期：2026-08-18
- 最近更新：2026-08-18
- 优先级：`P1`
- 需求明确状态：`已明确`
- 审批状态：`已批准`
- 实现状态：`已实现待验证`
- 用户原始描述：“仓库看不到存的东西，我还希望仓库可以在不改变容量的情况下只允许存一类东西。”“没看到石料的矿。增加所有矿物图标，自动浮现在矿点上，材料图标也需要。”“当我材料不足点击放置建筑的时候，告诉我缺少什么。”用户同时要求修复旋转并增加预览，该故障单独登记为 `BUG-0006`。
- 设计动机：让仓储、资源位置、材料含义和建造失败原因都能从正式 3D 画面直接理解，闭合自然开局的石料获取缺口，并停止把仓库只当作不可观察的容量倍率。
- 目标体验：玩家选中仓库即可查看真实内容、剩余共享空间和过滤；矿点在世界中自动显示对应图标、名称与储量；所有材料在 HUD、背包、合成、仓库、科技与成本中使用一致图标；材料不足时直接看到逐项缺口。
- 已批准的仓库规则：
  1. 每座已完成、归玩家所有且未进入撤离锁定的仓库拥有独立共享库存，固定总容量 `150`；仓库不再为每种资源分别复制 `+150` 容量。
  2. 仓库过滤可设为“不限”或一个既有稳定资源 ID。过滤不改变 `150` 总容量，只限制后续入库；已有不兼容内容未清空时拒绝切换，不自动删除、转换或迁移物资。
  3. 仓库面板显示真实内容、图标、数量、总占用、剩余空间、过滤与物流连接。自动物流和玩家转移共同遵守过滤、共享容量和原子回滚；脱离物流时保留内容与过滤但停止自动交换，重新连接后恢复。
  4. 城市资源总览聚合城市核心和有效仓库的实际存量；每种资源的可用容量按城市核心基础容量、仓库现有同类内容、过滤和未占用共享空间计算，不把同一空位同时承诺给多个资源。聚合、路由和事务属于运行时规则层，UI 只读快照。
  5. 仓库内容与过滤首版保持 3D 会话态，不修改 schema `30`；冻结 2D 不接线。
- 已批准的资源节点与图标规则：
  1. `WorldMapModel` 继续是资源类型、坐标和剩余储量唯一真值。seed `8128` 在既有 `32×24` 内容区确定性提供至少一个可到达的石料节点；`IDEA-0006` 新增外圈仍不新增资源。
  2. 采矿站兼容铁矿、能晶和石料节点，并每 `3` 秒产出 `1` 单位节点对应真实资源；不新增资源类型或石料后续加工链。
  3. 所有世界资源节点自动显示对应资源图标、正式名称与剩余储量。全部 `15` 种既有资源通过同一稳定图标目录供世界节点、资源栏、背包、合成、仓库、科技成本和建造成本复用；缺少正式美术时使用清晰、可替换的占位图标。
- 已批准的精确缺料规则：放置预览和玩家点击确认时都从正式建筑成本与当前可访问库存快照计算缺口，并逐项显示“资源名、拥有量、需要量、缺少量”；不得只返回“材料不足”，也不得由 UI 复制成本或库存真值。
- 不包含的范围：新资源类型、新生产链、传送带、跨城市运输、仓库优先级网络、正式仓库/背包存档迁移、schema 修改、冻结 2D 接线、敌人、炮塔和战斗。

- 目标体验：玩家完成“自动防御”研究并建成首座机枪塔后收到 `15` 秒清晰预警；`8` 只啃噬者在 `40` 秒内分批直达城市核心；机枪塔自动选择射程内目标并消耗本地弹药，玩家能够从 HUD 和选中详情理解城市核心、波次、敌人、炮塔和弹药状态。
- 已批准的科技与炮塔规则：
  1. `core.research.automated-defense` 从锁定预览改为正式可研究，继续使用 A16.4 的前置、成本和时间：前置“弹药装配”，消耗 `12` 合金和 `10` 生物质，耗时 `35` 秒；完成后解锁机枪塔。`加固结构` 和 `遗产解析` 仍为 `PreviewOnly`，不可启动且不接入效果。
  2. 机枪塔使用 `20` 基础 DPS、`10` 格射程和 `30` 弹药本地库存。每 `1` 单位弹药支撑累计 `3` 秒有效射击；没有有效目标时不消耗弹药。伤害和耗弹由确定性规则时间计算，tracer 只作表现，不持有命中或伤害真值。
  3. 机枪塔在物流范围内通过现有城市仓储入口补充弹药；脱离物流后保留本地弹药并可继续射击直到耗尽，但不能访问城市库存或自动补给；重新接入后恢复补给。不得复制物流范围、仓储路由或资源事务判断。

  2. 第一轮敌人只以城市核心为目标并直接接近核心，不进行建筑/城墙目标选择、阻挡绕行或寻路。首座已完成机枪塔触发唯一教学波：预警 `15` 秒，随后 `8` 只啃噬者在 `40` 秒内确定性分批生成。
  3. 城市核心使用既有 A16.1 基线 `2000 HP`；啃噬者进入 `2` 格攻击距离后按 `8 DPS` 造成规则伤害。核心归零属于可观察的失败状态，但本轮不扩大到正式结算、检查点或存档迁移。
- 已批准的暂停与可观察规则：

  2. 全局战术暂停和系统菜单暂停冻结预警、生成、移动、攻击、索敌、射击、耗弹、伤害以及相关规则计时；关闭暂停后从保留的确定性进度继续，不以暂停覆写单塔自己的暂停状态。

## 10. 标准更新流程

### 10.1 新增反馈

1. 先在对话中保留用户原始意图，不直接修改本文件；
2. 逐项确认修改位置、目标规则、原文冲突、版本边界和验收方式；
3. 向用户展示最终摘要，得到明确确认；
4. 分配下一个未使用的稳定编号；
5. 在当前待处理总表和对应类型章节增加记录；
6. 标记真实的需求明确、审批和实现状态；
7. 提交并推送当前开发分支。

### 10.2 用户批准或拒绝

1. 确认需求明确状态为 `已明确`；
2. 更新审批状态和最近更新时间；
3. 填写决策原因；
4. 若为 `已批准`，补齐验收条件和影响范围；
5. 若改变原文档，同步修改原文档并建立双向引用；
6. 单独提交并推送。

### 10.3 开发与验证

1. 开始设计或实现时标记为 `开发中`；
2. 实现提交完成后标记为 `已实现待验证`，填写提交哈希；
3. 通过规定测试、构建或人工验收后标记为 `已验证`；
4. 填写验证命令、结果或人工验收日期；
5. 将已验证记录移入已关闭记录；
6. 单独提交并推送。

## 11. GitHub 同步规则

这里的“实时更新”指：每次用户明确新增反馈或改变状态后，在同一工作流程内完成文档修改、Git 提交和 GitHub 推送。

- 每次新增记录、批准、拒绝、撤回、开始开发、实现完成或验证完成都应独立提交；
- 使用普通推送，不使用强制推送；
- 未经用户明确授权，不合并默认分支、不创建公开 Release；
- GitHub 暂时不可用时先本地提交，恢复连接后按原顺序推送；
- 不为补写记录而改写已经推送的历史；
- 不提交账号凭据、Unity 许可证、本机缓存、临时构建或机器专用绝对路径；
- 提交前必须确认暂存区只包含本次记录和相关正式文档。

## 12. 每次开发的回写要求

开发者完成任务前必须检查：

- 是否引用了相关 `BUG-`、`IDEA-` 或 `DOC-` 编号；
- 需求明确状态是否允许当前审批或开发；
- 审批状态是否允许当前开发；
- 实现状态是否与真实完成度一致；
- 是否填写实现提交；
- 是否填写验证证据；
- 是否同步修改受影响的主 GDD 或路线图；
- 是否已将补充文档更新推送到 GitHub。
