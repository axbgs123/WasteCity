## 1. 开发前必读

所有人类开发者和 AI 开发代理在分析、设计、计划、编码、测试或修改文档前，必须先阅读本文件。

本文件统一用于：

1. 反馈测试或试玩中发现的 Bug；
2. 登记用户提出的新构思；
3. 申请改变主 GDD、正式路线图或其他原有文档；
4. 标记每项内容的需求是否已经明确、是否已经批准、是否已经实现、是否完成验证。

核心规则：

> 需求明确不等于批准，批准不等于实现，实现不等于验证。

用户提出 Bug、新构思或文档修改后，必须先通过对话澄清修改位置、目标规则、版本边界和验收方式。澄清期间不得直接写入本文件。开发者应先向用户展示需求摘要与原文差异；只有用户确认摘要后，才能登记记录、更新正式文档或改变审批状态。尚未批准的内容不得扩大开发范围或进入代码实现。

## 2. 权威边界

- 已运行代码、自动化测试和构建结果代表当前已经实现的事实；
- 主 GDD 代表正式版产品与系统目标；
- 正式路线图代表已批准功能的实现顺序；
- 本文件代表用户最新反馈、审批决策、实现进度和验证证据；
- `已批准` 的文档变更必须先同步到对应正式文档，并在两处建立双向引用；
- 本文件中的计划、讨论或批准内容不得被描述成已经实现。

## 3. 状态定义

### 3.1 需求明确状态

| 状态 | 含义 | 是否允许申请批准 |
|---|---|---|
| `待澄清` | 仅有原始反馈，修改位置、目标行为或验收边界尚不完整 | 否 |
| `澄清中` | 正在与用户逐项对齐，尚未形成最终摘要 | 否 |
| `已明确` | 用户已确认需求摘要、原文差异、版本边界和修改方式 | 是 |

需求明确状态只描述“要做什么是否说清楚”，不代表用户已经批准开发，也不代表功能已经实现。

### 3.2 审批状态

| 状态 | 含义 | 是否允许开发 |
|---|---|---|
| `待确认` | 已登记，等待用户决定 | 否 |
| `已批准` | 用户明确同意进入正式流程 | 是 |
| `已拒绝` | 用户决定不采用 | 否 |
| `已撤回` | 用户取消此前的请求 | 否 |

### 3.3 实现状态

| 状态 | 含义 |
|---|---|
| `未实现` | 正式需求可以已经同步，但尚未开始代码、美术或运行时实现 |
| `开发中` | 正在设计、计划或实施 |
| `已实现待验证` | 修改已完成，但尚未满足全部验收条件 |
| `已验证` | 已有对应提交及测试、构建或人工验收证据 |
| `不适用` | 仅作澄清或决策，无需产生实现 |

新记录默认状态必须是：

```text
需求明确状态：待澄清
审批状态：待确认
实现状态：未实现
```

禁止直接从 `未实现` 跳到 `已验证` 而不填写实现提交和验证证据。

## 4. 稳定编号与优先级

### 4.1 稳定编号

- 测试 Bug：`BUG-0001`
- 新构思：`IDEA-0001`
- 文档变更：`DOC-0001`

三类编号分别单调递增。已关闭、拒绝或撤回的编号永久保留，不得复用。

### 4.2 优先级

| 优先级 | 使用条件 |
|---|---|
| `P0` | 无法启动、崩溃、坏档、核心流程无法继续 |
| `P1` | 核心玩法错误、严重数值或交互问题 |
| `P2` | 普通功能、表现、易用性或文档问题 |
| `P3` | 优化建议、远期构思或低影响调整 |

优先级不替代审批。即使是 `P0` 新需求，也必须由用户确认范围；可复现的故障允许先诊断，但修复仍应记录验收条件。

### BUG-0001：建造菜单不显示可建造内容

- 提出日期：2026-08-04
- 最近更新：2026-08-05
- 优先级：`P1`
- 需求明确状态：`已明确`
- 审批状态：`已批准`
- 实现状态：`不适用`
- 用户原始描述：建造菜单按下后不显示可建造的东西。
- 运行环境：macOS 15.6，Unity `2022.3.62f1`，`FormalPrototype` 场景 Play 模式。
- 复现步骤：
  1. 在 Unity 中打开 `Assets/_Game/Scenes/FormalPrototype.unity`；
  2. 进入 Play 模式并开始新游戏；
  3. 进入可操作场景后按 `B` 打开建造菜单；
  4. 查看建造菜单是否显示可建造建筑。
- 预期结果：建造菜单清晰显示当前可选择的建筑；已获得线索但条件不足的建筑显示锁定原因；隐藏建筑、尚未接触的路线建筑和唯一特殊建筑不进入普通列表；玩家可以使用键鼠稳定选择。
- 实际结果：按下建造菜单后，没有显示可建造的内容。
- 影响范围：玩家无法确认、选择和放置建筑，阻断基础建造与生产流程。
- 关联正式文档：`Docs/01-Game-Design-Document-ZH.md`、`Docs/05-Formal-Development-Roadmap-ZH.md`、`Docs/superpowers/specs/2026-08-05-3d-building-placement-and-developer-modifier-design.md`
- 关联提交：—（用户决定不修复，因此没有修复提交）
- 验收条件：准确保留原始描述、运行环境和复现事实；明确本问题只属于冻结 2D `FormalPrototype`，决定不修复且没有修复提交；默认 3D 的新建造功能不得计作本问题的修复。
- 验证证据：用户于 2026-08-05 明确批准“不修复冻结 2D 历史问题”的处置；本状态只记录决策，不构成代码修复或问题已解决的证据。
- 决策原因或备注：2D 功能基线已经冻结，默认编辑/构建入口已切换到独立 3D 场景；用户决定不再为冻结 2D 建造菜单追加专属交互。审批状态“已批准”指处置决定已批准，实现状态“不适用”指无需产生实现，不能解释为已修复。新的 3D 建造系统属于 `IDEA-0003` 新功能。

### BUG-0002：默认 3D 场景按 F 后城市没有展开

- 提出日期：2026-08-11
- 最近更新：2026-08-11
- 优先级：`P1`
- 需求明确状态：`已明确`
- 审批状态：`已批准`
- 实现状态：`已实现待验证`
- 用户原始描述：按下 `F` 后没有展开城市。
- 运行环境：macOS，Unity `2022.3.62f1`，默认 `GrayboxPrototype3D` 场景 Play 模式，seed `8128` 的第一版地表运行时接入版本。
- 复现步骤：
  1. 打开 `Assets/_Game/Scenes/GrayboxPrototype3D.unity`；
  2. 进入 Play 模式，保持城市位于默认出生位置；
  3. 按下 `F`；
  4. 观察城市模式、外观和界面反馈。
- 预期结果：默认出生位置必须允许玩家立即完成第一次展开；按 `F` 后城市进入 `Deploying` 并在既定三秒后进入 `Fortress`。玩家后来在不合法地形尝试展开时仍应被规则拒绝，但必须看到明确失败原因。

- 目标体验：玩家持续控制文明，并通过当前领袖直接行动；领袖倒地后需要作出救援与城市调度决策，永久死亡造成真实损失但不直接结束游戏。
- 已确认规则：
  - 领袖是玩家当前直接操控的文明角色，不是不可替代的玩家本体；玩家控制权随合法继任者延续；

  - 成功救援后进入重伤恢复，可能因救援延迟、重复倒地或特殊伤害留下永久伤势；不同路线可通过义体、生物改造、丹药或灵能治疗缓解；
  - 超时后永久死亡，遗体与装备留在现场；可派角色或城市回收，装备可能损坏或被其他势力夺走；
  - 领袖死亡后由临时议会低效维持城市；若长期没有合格继承人，触发紧急选举并产生能力较弱、政治代价更高的临时领袖；

- 不包含的范围：当前 Demo 不实现永久死亡、继承政治、内战或多候选人界面；不把领袖死亡直接视为文明失败。

### IDEA-0005：移动城市研究站与全状态研究效率

- 提出日期：2026-08-11
- 最近更新：2026-08-11
- 优先级：`P1`
- 需求明确状态：`已明确`
- 审批状态：`已批准`
- 实现状态：`开发中`
- 用户原始描述：移动城市研究站放不了；研究全程可以进行，但移动时速率减少。
- 设计动机：研究站属于城市长期发展的核心设施，不应因为城市迁移而被迫拆除或完全停止研究；同时保留展开堡垒的效率优势。
- 目标体验：玩家可以在移动城市内城建造并携带研究站；未来研究系统接入后，研究在四种城市状态间不中断，堡垒态效率最高，迁移过程效率减半。
- 已确认规则：
  - `ResearchStation` 允许建在移动城市内城并随城移动，运行标签从仅堡垒改为移动可用；
  - 堡垒态研究速度为 `100%`；移动、展开中、收起中均为 `50%`；状态切换不取消当前研究、不清空进度；
  - 本次实现只修改研究站的移动建造与携带资格，不新增研究菜单、科技选择、研究队列或研究推进控制器；
  - 在后续正式实现研究运行时时，必须使用本条效率规则，不得继续沿用冻结 2D 原型中“非堡垒完全暂停”的旧行为；
  - 其他建筑的位置、运行标签和城市模式限制保持不变。
- 不包含的范围：研究 UI、科技树交互、研究队列、研究资源消耗、存档迁移、研究动画与正式研究站模型。

### IDEA-0011：3D 生产物流、背包、应急合成、首版科技树与资源状态栏

- 提出日期：2026-08-17
- 最近更新：2026-08-17
- 优先级：`P1`
- 需求明确状态：`已明确`
- 审批状态：`已批准`
- 实现状态：`已实现待验证`
- 用户原始描述：“你自行决定，另外我需要背包，还有科技树，一些材料或者元素，资源状态栏也需要。背包参考异星工厂，科技树你自己决定。资源状态栏参考文明。”本轮同时承接已交接的“生产与物流可观察化”目标，先完成机枪塔之前的生产闭环，不进入敌人、炮塔或战斗开发。
- 设计动机：此前的 3D 主循环已经具备建筑目录、统一放置与施工、资源节点真值、城市状态和物流范围等基础，但尚无可供玩家理解和操作的正式生产闭环。本轮已用背包、受控应急合成、首版科技推进和文明式资源总览补足“获得资源—加工—解锁—观察—调度”的最小玩法循环，最终验证仍待完成。
- 目标体验：玩家能在正式 3D 输入/UI 主循环中观察采矿、冶炼和装配的实时运行状态，通过城市物流或近距离建筑缓存转移资源，在 30 格背包中管理物资并进行有限的应急合成，通过六节点首版科技树解锁前两项实际能力，并从常驻资源栏快速判断库存、容量与净流速。
- 已批准的生产与物流规则：
  1. 采矿站无输入，每 `3` 秒从其绑定节点生产 `1` 单位该节点的真实资源：铁矿节点产出铁矿，能晶节点产出能晶；本轮完整加工链只消费铁矿。冶炼厂每 `6` 秒消耗 `2` 铁矿并生产 `1` 合金；装配厂每 `6` 秒消耗 `2` 合金并生产 `2` 弹药。上述周期是 3D 首版的最终有效周期，不叠加冻结 2D 的要塞生产倍率；数值必须来自正式配置，不得散落硬编码。
  2. 稳定供应关系为 `2 采矿站 → 2 冶炼厂 → 1 装配厂 → 1 座持续射击机枪塔`；本轮只实现和观察机枪塔之前的生产部分。
  3. 每座生产建筑拥有内部输入/输出库存。展开城市提供既有物流范围；范围内建筑通过统一自动物流步骤与城市库存交换资源且不要求相邻，生产周期本身只消费建筑缓存。本条最初批准的“每座仓库为每种资源分别增加 `150`”容量模型已被用户于 2026-08-18 批准的 `IDEA-0012` 替代：仓库改为真实独立的 `150` 共享总容量与可选单资源过滤，具体以 `IDEA-0012` 和当前 GDD 为准。
  4. 建筑离开物流范围后保留内部库存，不能访问城市库存或其他建筑缓存；若本地仍有足够输入和输出空间，可继续运行，直到输入耗尽、输出已满或资源节点枯竭。重新进入范围后恢复既有访问关系。
  5. 资源节点储量与枯竭必须以 `WorldMapModel` 为唯一真值；放置兼容性、城市物流范围和建筑合法性必须复用现有统一规则，不得复制判断或另建影子状态。
  6. UI 必须显示且规则层必须稳定区分五种停工原因：缺少输入、输出已满、不在物流范围、矿脉已枯竭、玩家暂停运行。首版“脱离物流”保持单一状态，不提前拆分电力、维护或通信。
  7. 玩家对单座建筑的运行暂停独立于全局暂停；全局暂停冻结生产、合成和研究时间，不得借此改写建筑自身停工原因。
- 已批准的背包与转移规则：
  1. 玩家会话持有一个 `10×3`、共 `30` 格的背包；每格同种资源最多堆叠 `100`。首版不为背包增加正式存档迁移，schema 保持 `30`。
  2. `E` 打开或关闭统一“背包 + 合成”界面。背包格交互采用左键拿取/放下整堆、右键拆半或逐个放置、`Shift + 左键` 在当前可访问库存之间快速转移；这些背包手势不得与合成次数手势混用。
  3. 背包可与城市库存、当前选中建筑的内部缓存进行显式原子转移。目标容量不足时先计算实际可接收量，并只对该实际量执行一次原子扣除与加入；实际量为零、来源不足或访问条件不满足时不发生转移并显示原因。任一提交步骤失败时完整回滚，不得丢失或复制资源。
  4. 直接访问任意建筑缓存时，建筑必须已完成、归玩家所有且未进入撤离锁定，并且玩家当前直接控制的目标（城市或已招募领袖）距该建筑 footprint 边缘不超过 `2` 格；联网状态不能绕过该距离。脱离物流只表示该近距离人工操作不要求自动物流连接。直接控制城市时始终允许访问该城市库存；直接控制已招募领袖时，领袖距城市核心 footprint 边缘不超过 `2` 格才允许访问城市库存。
- 已批准的应急合成规则：
  1. 只提供两项应急配方：完成“基础冶金”后可用 `4 铁矿 → 1 合金 / 12 秒`；完成“弹药装配”后可用 `4 合金 → 2 弹药 / 12 秒`。配方输入从背包原子预留，产物返回背包。
  2. 合成次数手势为左键加入 `1` 次、右键请求完整加入 `5` 次、`Shift + 左键` 加入当前输入材料与队列余量共同允许的最大次数。右键请求若无法完整承担 `5` 次则整体拒绝，只有 `Shift + 左键` 会自动缩减为最大可承担次数。合成队列按 FIFO 执行，总计最多容纳 `20` 次配方执行；入队时一次性原子预留该批全部输入，不预留输出空间，也不能部分扣除。
  3. 取消尚未完成的项目时 `100%` 返还预留输入；返还空间不足则拒绝取消。产物无可用空间时当前项目阻塞，不丢弃产物，也不跳过到后续项目。
  4. 关闭 `E` 界面后队列继续；统一暂停冻结计时。首版不自动串联合成前置材料，也不扩展为通用手工制造系统。
- 已批准的科技树规则：
  1. 首版按 GDD A16 的六节点建立：`废料加工` 初始已完成；`基础冶金`、`弹药装配` 是本轮仅有的可实际研究节点；`自动防御`、`加固结构`、`遗产解析` 可见但锁定为预览，不可启动。
  2. `基础冶金` 前置为废料加工，消耗 `10` 铁矿、耗时 `20` 秒，解锁冶炼厂机器配方和合金应急合成；`弹药装配` 前置为基础冶金，消耗 `10` 合金、耗时 `30` 秒，解锁装配厂机器配方和弹药应急合成。
  3. 三个预览节点继续显示 A16 数值与依赖：自动防御前置弹药装配，`12` 合金 + `10` 生物质、`35` 秒；加固结构前置自动防御，`20` 合金 + `10` 生物质、`45` 秒；遗产解析前置自动防御，`30` 合金 + `20` 生物质、`60` 秒。它们本轮均不可启动，不提前接入效果。
  4. 开始和推进研究都必须依赖至少一座已完成、归玩家所有且未进入撤离锁定的研究站；失去最后一座合格研究站时暂停但不取消、不退款，恢复后继续。要塞形态研究效率 `100%`，其他城市状态 `50%`。开始研究时从城市库存扣除全部成本；取消返还 `80%` 并清零进度，若完整退款无法原子写回城市库存则拒绝取消；首版不增加研究队列。
  5. 当前代码中的完整 `43` 节点路线不作为本轮运行时科技树。六节点投影复用四个已有 ID：`core.research.automated-machinery`、`core.research.precision-assembly`、`core.research.automated-defense`、`core.research.legacy-analysis`；批准新增仅属于 3D 六节点语义的 `core.research.scrap-processing` 与 `core.research.reinforced-structures`。不得为已有语义再建平行 ID，也不得静默改写四个既有 ID。双资源科技成本必须先进入正式配置模型，不能写成 UI 特例。
- 已批准的资源状态栏规则：
  1. HUD 常驻显示五种基础资源：铁矿、能晶、石料、生物质、水；合金和弹药在首次发现或相应科技解锁后加入常驻栏。以上名称作为本轮正式显示名，由统一资源目录提供。

  3. 点击资源栏打开完整资源账本，列出既有全部 `15` 种 `ResourceId`；未发现资源可以保持零值或未知表现，但不得创建新的资源类型或第二套账本真值。

## 10. 标准更新流程

### 10.1 新增反馈

1. 先在对话中保留用户原始意图，不直接修改本文件；
2. 逐项确认修改位置、目标规则、原文冲突、版本边界和验收方式；
3. 向用户展示最终摘要，得到明确确认；
4. 分配下一个未使用的稳定编号；
5. 在当前待处理总表和对应类型章节增加记录；
6. 标记真实的需求明确、审批和实现状态；
7. 提交并推送当前开发分支。

### 10.2 用户批准或拒绝

1. 确认需求明确状态为 `已明确`；
2. 更新审批状态和最近更新时间；
3. 填写决策原因；
4. 若为 `已批准`，补齐验收条件和影响范围；
5. 若改变原文档，同步修改原文档并建立双向引用；
6. 单独提交并推送。

### 10.3 开发与验证

1. 开始设计或实现时标记为 `开发中`；
2. 实现提交完成后标记为 `已实现待验证`，填写提交哈希；
3. 通过规定测试、构建或人工验收后标记为 `已验证`；
4. 填写验证命令、结果或人工验收日期；
5. 将已验证记录移入已关闭记录；
6. 单独提交并推送。
