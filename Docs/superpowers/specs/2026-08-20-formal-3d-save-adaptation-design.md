**日期：** 2026-08-20

**需求：** `IDEA-0015`

**状态：** 用户已批准需求与规则；本文为正式设计规格；代码、自动化、构建、用户试玩与 Windows 实机验证均尚未完成

**目标场景：** `Assets/_Game/Scenes/GrayboxPrototype3D.unity`

**兼容场景：** 冻结 2D `Assets/_Game/Scenes/FormalPrototype.unity`，仅在退役门完成前保留兼容回归，不接新玩法

**Unity：** `2022.3.62f1`

## 1. 权威性与实施边界

本文把 `Docs/06-User-Feedback-and-Change-Control-ZH.md` 中已批准的 `IDEA-0015` 转化为可执行的数据合同、运行时所有权、文件事务、恢复顺序、检查点、错误和退役设计。后续实施计划可以细化任务与文件名，但不得改变本文规则。若实施发现必须改变玩法数值、引入 schema `32`、把旧 2D 档静默转换为 3D，或删除尚未通过退役门的兼容代码，必须停止并回到变更控制。

当前 `FormalSaveData`、`FormalSaveCodec` 和 `FormalSaveController` 是 schema `1–30` 的冻结 2D 实现。它们存在以下已确认限制：

- schema `30` 是扁平的 2D 数据，不能表达正式 3D 的稳定建筑实例、真实仓库、背包、合成、逐建筑生产、防御和已确认撤离；
- `FormalSaveController` 直接写正式文件，写前复制备份，但没有同目录临时文件、刷新后复读、语义校验和原子替换；
- `HasSave` 只依据文件存在，不代表该文件可解码、可验证或可用于当前运行时；
- schema `1–30` 的兼容规则散布在 2D `Apply` 分支中，未知建筑可能被静默跳过；
- 默认 3D 场景没有正式存档控制器，现有防御观察快照也不含继续确定性模拟所需的全部内部累积量。

本阶段不复用或改写 schema `30` 字段来伪造 3D 状态。schema `31` 是独立、明确标识为正式 3D 的完整 payload。项目最终只保留一套存档基础设施；冻结 2D 与正式 3D 在过渡期只是该基础设施的两个运行时适配器。

## 2. 目标与非目标

### 2.1 目标体验

玩家必须能够：

1. 在默认 3D 入口开始新游戏；
2. 由事件驱动的自动检查点保护当前垂直切片进度；
3. 从系统菜单执行“保存并退出”；
4. 重开游戏后从最近有效的 schema `31` 存档继续；
5. 在活动展开/收起、活动战斗或已确认撤离及容量阻塞中保存并恢复，而不是被拒绝、重置或丢弃状态；
6. 在主档损坏时回退最近有效备份，并看到准确中文说明；
7. 在默认 3D 入口遇到 schema `1–30` 旧 2D 档时看到明确兼容说明，不把旧档冒充为新 3D 世界。

“继续”表示存在经统一基础设施解码、哈希校验、语义验证且与当前运行时兼容的档案，不再表示某个路径上存在任意文件。

### 2.2 非目标

本阶段不实现：

- 多槽位、存档列表、云存档、跨设备同步或跨循环继承；
- schema `1–30` 到 schema `31` 的自动或隐式 2D→3D 世界转换；
- 外部 Mod 扫描、下载或管理界面；
- 前哨、多城市、跨城市运输、新敌人、新炮塔、新资源或玩法数值调整；
- UI 布局、选中、悬停、摄像机、蓝图预览、对象池、粒子、tracer、临时提示等表现态持久化；
- 逐帧、短周期轮询或崩溃日志式连续写盘；
- 在 schema `31` 尚未完成全部质量门前删除冻结 2D 专属文件。

未知内容的安全保存与可理解降级属于存档健壮性，不等于实现外部 Mod 系统。

## 3. 单一存档基础设施

### 3.1 唯一服务与逻辑单槽

全项目只允许一个正式 `SaveService`（名称可在实施中调整）拥有：

- 逻辑槽路径及其 `.tmp`、`.bak`、损坏隔离和迁移前备份命名；
- envelope/旧档分类、编码、解码、哈希和语义验证；
- schema 迁移注册表与旧 ID 映射；
- 原子写入、备份、候选选择和恢复结果；
- 一次只执行一个保存/加载事务的并发门；
- 结构化结果代码、诊断细节和玩家提示键。

逻辑单槽继续使用现有正式路径语义 `Application.persistentDataPath/formal-world.json`。`.bak`、`.tmp`、`.corrupt-*` 和 `.legacy-schema-*` 是该槽的恢复/归档工件，不是玩家可选择的额外槽位。任何场景适配器都不得自行拼路径、调用 `File.WriteAllText`、维护另一个备份或建立同义迁移器。

### 3.2 运行时适配器

统一服务通过窄运行时适配器工作：

- 冻结 2D 适配器只负责把 schema `1–30` 的旧 DTO 与 2D 领域模型互相映射；
- 正式 3D 适配器只负责把 schema `31` 的 `formal3D` DTO 与当前 3D 领域所有者互相映射；
- 适配器不拥有磁盘文件、备份、迁移和 UI 文案；
- 服务不通过场景搜索或反射抓取状态，所有领域引用由正式 authoring 显式接线。

schema `1–30` 的现有默认规则被冻结为兼容事实。实施时可以把它们从散布的 `Apply` 分支整理为命名迁移/兼容步骤，但不能改变同一 fixture 的解码结果。

### 3.3 类型分类先于恢复

统一解码入口先分类，再选择 codec：

| 输入 | 分类 | 默认 3D 行为 |
|---|---|---|
| `saveSchemaVersion == 31` 且 `runtimeKind == "formal-3d"` | 正式 3D | 完整验证后允许继续 |
| 旧扁平根 `schema` 为 `1–30` | 冻结 2D | 可解码、可验证；不应用到 3D，显示兼容说明 |
| schema 大于当前支持版本 | 未来版本 | 拒绝加载，保留原文件 |
| JSON 可解析但类型标识/必要 payload 不一致 | 类型损坏 | 拒绝加载并尝试有效备份 |
| 非法 JSON、哈希不符或语义无效 | 损坏 | 隔离主档并尝试有效备份 |

不得根据“缺字段就填默认值”的方式把旧档分类成 3D。分类器也不得依赖文件名或当前场景猜测类型。

## 4. schema `31` envelope 与独立 3D payload

### 4.1 顶层合同

schema `31` 顶层固定为非多态、可确定性序列化的 envelope：

```text
FormalSaveEnvelopeV31
  saveSchemaVersion = 31
  runtimeKind = "formal-3d"
  gameVersion
  contentSources[]
  createdAt
  updatedAt
  payloadHashSha256
  checkpoint
  formal3D
```

字段规则：

- `gameVersion` 使用构建提供的正式版本字符串；不从 UI 文本读取；
- `contentSources` 至少包含内置内容来源及版本，按稳定 ID 排序；本阶段不主动扫描外部 Mod；
- `createdAt` 与 `updatedAt` 使用 UTC ISO-8601 往返格式；`createdAt` 在同一 3D 进度首次保存后保持不变，`updatedAt` 每次成功写入更新；
- `payloadHashSha256` 是 `formal3D` 紧凑规范 JSON UTF-8 字节的 SHA-256 小写十六进制值；解码后必须重新规范编码并比较；
- `checkpoint` 保存单调递增序号、稳定原因 ID、触发时规则时间和已完成的一次性里程碑 ID；玩家文案不写入存档；
- `formal3D` 是唯一 3D payload。envelope 不同时携带 2D 字段，也不使用 `FormalSaveData.schema`。

所有 DTO 使用显式可序列化字段和数组，不直接序列化 Dictionary、HashSet、Unity `Object`、只读属性对象或运行时接口。数组在捕获时按本文指定的稳定顺序排序，空集合编码为空数组而不是依赖 `null`。

### 4.2 schema `1–30` 兼容边界

schema `1–30` 保持原扁平 JSON 形状、现有版本门和既有默认值。固定 fixtures 至少覆盖最早 schema `1`、当前完整 schema `30`，以及实施中实际抽取或改动兼容分支所涉及的代表性版本；另以参数化测试逐一证明 `1–30` 都仍被识别为旧 2D，而不是为每个整数版本复制一份大型 fixture。兼容测试必须证明：

- 旧档仍可分类、解码和验证；
- 同一 fixture 的迁移后 2D 语义不因 schema `31` 实施改变；
- 默认 3D 入口从不调用 2D `Apply`；
- 旧档不会生成背包、3D 建筑、逐建筑生产、3D 防御或撤离的伪造默认状态；
- 未来 schema 被拒绝，而不是按当前 schema 尝试读取。

若逻辑槽里已有有效 schema `1–30` 档，默认 3D“继续”不可用并显示说明。玩家明确选择“开始新的 3D 游戏”后，首次 3D 写入必须先把旧档逐字节保存为经过复读验证的 `.legacy-schema-{n}-{timestamp}.json` 归档，再写 schema `31`；归档不出现在槽位 UI，也不被静默删除。仅查看或尝试继续旧档绝不能覆盖它。

## 5. 领域权威字段与派生字段

### 5.1 总原则

保存“恢复后若不同会改变玩法结果或玩家资产”的事实；不保存“可以由这些事实和正式配置稳定重算”的投影。容量、配方、建造成本、研究前置、伤害数值和时长来自正式 catalog/GDD，不复制为第二套可变配置；但为未知内容降级所需的原始稳定 ID、占格和已预留资产必须保留。

### 5.2 世界与资源节点

权威字段：

- `worldDefinitionId`、`worldGenerationVersion`、seed、地图尺寸/签名；
- 每个资源节点的稳定 node ID、格位、资源稳定 ID、剩余量和枯竭标志；
- 当前世界内为兼容保留的未知/孤立资源记录。

节点按稳定 ID 排序。恢复时用 `WorldMapModel` 和正式世界配置重建地形、通行和节点索引，再按稳定 node ID 应用可变量。格位、资源类型和地图签名用于交叉验证，不能另建第二套资源节点真值。

派生且不保存：地形表现、矿点图标、可见提示、寻路图缓存、节点查询字典、采矿站的“已枯竭”停工原因。

### 5.3 城市、部署、导航与人口

权威字段：

- 城市世界位置/权威格位；
- 自动驾驶是否活动及目的地格位；
- `CityMode`、活动 Deploying/Packing 的基础规则剩余秒和取消应返回的稳定模式；
- 当前人口与人口容量；
- 玩家持久选择的全局战术暂停；
- 检查点一次性里程碑和下一个稳定序号等防止 ID 重用的计数器。

自动驾驶路径由 `WorldMapModel` 在加载后从当前位置和目的地重新寻路；刚体速度归零并由控制器重建。物流半径来自城市模式、位置和正式规则。开发修改器、开发时间倍率、系统菜单暂停、加载内部暂停、输入按键状态和摄像机不保存。

### 5.4 建筑会话

每个 `GrayboxBuildingInstance3D` 保存：

- 稳定实例 ID、建筑 definition ID；
- Ground/Inner 站点、格位、方向；
- UnderConstruction/Completed/AbandonedRuin 状态、施工基础剩余秒、玩家所有权；
- 绑定资源节点稳定 ID 与格位；
- 为未知建筑占位恢复保存的原始 footprint/站点兼容信息；
- 会话 `nextStableInstanceOrdinal`。

实例按稳定实例 ID 排序。Ground/Inner `BuildingGrid`、占格索引、catalog revision、placement revision、表现 GameObject、材质和选择状态由实例列表重建。`IsEvacuationLocked` 的最终值由已确认撤离批次重放；建筑记录可带锁交叉校验值，但不得形成独立可修改的第二真值。

未知建筑不被静默跳过。它恢复为不可运行的“缺失内容占位体”，保留原始 ID、位置、占格、方向、所有权和内部资产引用，并向玩家给出内容缺失警告；它不能生产、建造或绕过放置合法性。官方 ID 改名先经过不可变旧→新映射。

### 5.5 城市账本与仓库

权威字段：

- 城市核心账本中每个资源稳定 ID 的实际数量；
- 每座仓库的建筑稳定实例 ID、单资源过滤 ID、实际内容；
- 未知资源的孤立资源表及其原所有者/容器标识。

仓库容量和城市核心单资源容量来自正式配置，不作为加载后可覆盖配置的值；存档可保存捕获时配置签名用于验证。加载必须验证非负、总量不溢出和同一资产不重复。若内容因正式配置变化暂时超过当前容量，原量不得静默截断：该容器进入可理解的超额只出不进状态，直到玩家清理。

派生且不保存：仓库 `IsConnected`、网络总量、可接受空间、稳定路由计划、物流范围结果、聚合容量、revision 和 UI 资源总览。

### 5.6 30 格背包与应急合成

背包保存固定 `30` 个有序槽位；每格保存索引、资源稳定 ID和数量，空格也必须可确定性表达。加载验证堆叠上限、非负数量和唯一槽索引；未知资源保留在原格的孤立占位堆叠中，不可用于配方但不能丢失。

合成保存：

- 最多 `20` 个有序执行项；
- 每项 recipe 稳定 ID和该次入队时实际预留的输入快照；
- 活动首项进度秒；
- 必要的下一个队列序号。

当前 `CraftingQueueModel` 在入队时已从背包扣除输入，因此恢复顺序是“原样恢复背包，再恢复队列且不重复扣料”。保存每项预留输入不是第二份可消费库存，而是该排队执行项的资产归属和未来未知配方退款依据。实现必须提供专用 capture/restore API，不能通过公开 `TryEnqueue` 恢复。

配方定义、时长、输出、科技前置和 `OutputFull` 从 catalog/背包重算。未知 recipe 保留为暂停的缺失内容项，预留输入仍可安全取消返还；不得自动视为完成或吞掉预留。

### 5.7 研究

保存六节点研究模型的：

- 已完成科技稳定 ID 集合（编码时排序）；
- 活动科技稳定 ID；
- 活动项剩余规则秒。

科技成本已经在开始时支付，不重复保存或重复扣除。研究站资格、城市模式倍率、科技树连线、按钮状态、可研究原因和 UI revision 重算。未知已完成 ID 原样保留但不授予未知效果；未知活动项暂停并显示内容缺失，不自动完成或退款。

### 5.8 逐建筑生产

每个可保留的 `BuildingProductionState` 保存：

- 建筑稳定实例 ID和用于一致性校验的 recipe/definition ID；
- 内部 Input 中各资源实际量；
- `HasReservedInputs` 及已预留输入的资源/数量；
- Output 中各资源实际量；
- 当前周期进度秒；
- 玩家对该建筑设置的暂停；
- 采矿建筑的绑定 node ID/格位交叉引用。

状态按建筑稳定 ID 排序。输入/输出容量、配方、周期和物流资格来自正式配置。`IsLogisticsConnected`、`StopReason`、UI 状态和观察快照不保存；恢复建筑、城市模式和仓储后重新同步并计算。恢复 API必须直接建立内部状态，不能再次从城市库存预留输入。

### 5.9 防御、教学波与活动战斗

现有 `GrayboxDefenseRuntimeSnapshot3D` 只适合观察，不足以恢复确定性模拟。正式持久 DTO 必须由 `GrayboxDefenseRuntime3D`/纯防御模型显式 capture/restore，至少保存：

- 教学波是否已触发、触发次数、波阶段、预警剩余、spawn clock/固定步累积、已生成/已击败计数和下一敌人稳定序号；
- 城市核心当前生命；最大生命来自正式配置并以配置签名验证；
- 每个存活敌人的稳定 ID、archetype ID、spawn order、当前位置、当前生命、移动/攻击内部余量和持续攻击所需累积量；
- 每座机枪塔的建筑稳定 ID、本地弹药、玩家暂停、当前弹药剩余生效秒、伤害小数余量和固定步累积；
- 若未来防御使用随机数，保存该权威随机流状态，而不是重新取系统随机数。

敌人按 spawn order 后稳定 ID 排序，炮塔按建筑稳定 ID 排序。当前目标、目标距离、`Firing`/`NoTarget`/缺弹/脱离物流状态、tracer、敌人 GameObject 和池索引都由恢复后的权威状态重新选择/投影。恢复不能仅调用观察快照构造默认内部累积量，否则会改变下一次耗弹、伤害或攻击时点。

### 5.10 已确认撤离

未确认的清单面板、鼠标选择和临时分配是 UI 草稿，不保存。`ConfirmManifest` 成功并建立锁后，以下状态成为必须保存的权威事务：

- `activeBatchId`、`nextBatchOrdinal`、是否 processing；
- 确认时冻结的 `EvacuationBatchContext`：是否处于活动战斗、人口生产力倍率；开发时间倍率不进入该上下文；
- 按稳定规则冻结的全部 work：建筑 ID、处理方式、剩余比例、基础拆除秒、实际拆除秒和退款；
- 实际执行 `fullQueue` 顺序、当前 index/项目、剩余规则秒和玩家/全局暂停投影所需的权威暂停选择；
- 每项确认时捕获的生产输入、预留、输出、塔内弹药和仓库/内部资源载荷；
- 当前容量阻塞代码、阻塞项目 ID 和最后一次提交事务状态；
- 批次对应的建筑锁和为失败回滚保留的未提交项目集合。

容量缺口数值、中文失败句、队列 view revision 和 manifest view-model 由当前仓储重新计算；但“当前项目因容量不足而阻塞”及其稳定失败代码必须恢复，以免加载后自动越过尚未提交的项目。恢复撤离时不重新捕获运行时 payload、不重复锁定已完成项目、不重复退款，也不通过 `ConfirmManifest` 重走玩家确认。

## 6. 捕获事务

### 6.1 捕获屏障

一次完整捕获必须在规则帧边界执行：

1. 统一检查点编排器获得单事务门；若正在加载则返回 `Busy`，若保存正在进行则合并一个待处理原因；
2. 添加专用 `PersistenceCapture` 暂停原因，等待当前 FixedStep/领域提交结束；不把系统菜单或 `Time.timeScale` 当互斥锁；
3. 记录各领域 revision/稳定指纹起点；
4. 由每个领域所有者返回深拷贝 DTO，不读取 UI 快照、Renderer 或场景搜索结果；
5. 再次读取 revision/指纹；若捕获期间发生变化，丢弃 DTO并有限次重试，仍不稳定则返回“状态正在变化，请稍后再试”；
6. 完成跨领域语义验证和确定性排序；
7. 释放捕获暂停；之后只对冻结 DTO编码和执行磁盘事务，绝不在后台访问 Unity 对象。

捕获暂停只阻止规则推进和可变命令，不改变玩家原有战术暂停。异常路径必须在 `finally` 中释放自身暂停原因。

### 6.2 同一快照的捕获顺序

顺序固定为：

```text
metadata/checkpoint
  → world/resource nodes
  → city/deployment/navigation/population
  → building instances and next IDs
  → city core storage/warehouses
  → backpack
  → research
  → crafting queue and reservations
  → production internals
  → defense/combat internals
  → confirmed evacuation/locks/payloads
  → persistent tactical pause
```

顺序表达依赖，不允许前一领域在捕获后继续 tick。最终验证必须检查：所有 production/tower/warehouse/evacuation ID 都能对应一个允许保留的建筑；资源节点绑定存在或进入明确缺失内容状态；合成预留不同时出现在背包；已提交撤离项目不再存在于当前队列；所有量和时长有限、非负且在允许范围内。

## 7. 事务性恢复

### 7.1 恢复前预检

磁盘读取、候选分类、schema 迁移、哈希、字段和跨领域语义验证必须在任何场景状态改变前完成。预检还要验证当前内容 catalog、世界签名、稳定实例 ID 唯一性、格位占用、容量、资源归属、队列计数和撤离交叉引用。缺失的建筑、资源、配方或科技定义 ID 不能因此被静默删除或把整个档案一律判坏；它们按下一段进入缺失内容占位或孤立数据。只有 payload 内部引用了不存在的稳定实例、核心定义缺失或结构本身不自洽时才阻断恢复。

缺少可安全降级的普通内容时产生警告和占位体；缺少城市核心、世界生成器、必要基础资源定义或 payload 结构本身时属于阻断错误。验证器返回稳定错误代码和字段路径，不向 UI 抛异常。

### 7.2 两阶段应用与回滚

Unity 场景组件不能全部脱离场景构造，因此正式恢复采用“完整预检 + 受控应用 + 完整回滚”：

1. 进入专用 `PersistenceRestore` 暂停，停止输入命令、规则 tick、自动检查点和领域事件副作用；
2. 对当前有效 3D 会话捕获一份内存 rollback DTO；
3. 清理派生 UI、选择、预览、表现订阅和运行时缓存，但不销毁统一服务；
4. 按下列依赖顺序应用目标 DTO；每个领域使用专用 `ValidateRestore`/`Restore`，不得调用会再次支付成本、入队、触发波次或确认撤离的玩家命令；
5. 重建网格、物流、生产停工原因、研究资格、防御目标、仓储汇总和表现；
6. 执行一次完整后置语义验证并比较权威指纹；成功后才广播一次 `RestoreCompleted`，恢复玩家保存的战术暂停并解除内部暂停；
7. 任一步骤失败，屏蔽所有领域事件并用同一应用路径恢复 rollback DTO；回滚成功返回“加载失败，当前游戏未改变”；回滚也失败则保持内部暂停、显示阻断错误并要求安全返回标题，绝不能报告加载成功。

加载期间不触发自动检查点，不允许生产、研究、战斗或撤离推进一个 tick。

### 7.3 应用顺序

```text
1. world definition/seed/resource nodes
2. city position/deployment/navigation/population
3. building instances/grids/next stable ordinals
4. city core ledger/warehouses/filters
5. backpack slots
6. research
7. crafting queue/reservations (不重复扣料)
8. production internals (不重复预留)
9. defense core/wave/enemies/towers/internal accumulators
10. confirmed evacuation/work/payload/locks/blocking
11. persistent tactical pause
12. derived connectivity/status/paths/views/presentation
```

研究先于合成，是为了验证 recipe 前置但不重新消费；建筑与仓储先于生产/防御，是为了绑定稳定实例；生产/防御先于撤离，是为了恢复撤离内部载荷和锁。自动驾驶只恢复活动标志与目的地，路径在第 12 步重算。

## 8. 原子写、备份与损坏恢复

### 8.1 保存前验证

编码前对内存 DTO做完整语义验证并计算 `payloadHashSha256`。正式 JSON使用稳定字段顺序和紧凑 UTF-8；不得把本机绝对路径、异常堆栈或临时对象名写入 payload。

### 8.2 同目录文件事务

写入顺序固定为：

1. 在正式文件同目录创建唯一临时文件；
2. 使用 `FileStream` 写完整 UTF-8 字节并执行真正刷新到磁盘，关闭句柄；
3. 从临时文件重新读取，重新分类、解码、校验哈希和完整语义；
4. 若当前主档有效，把其字节写入备份临时文件、刷新、复读验证，再原子替换 `.bak`；无效主档绝不能覆盖有效备份；
5. 使用同卷原子替换把已验证临时文件变为主档；主档不存在时使用同目录原子 rename；平台不支持 `File.Replace` 时由唯一文件系统适配器执行有恢复标记的同卷 rename 方案；
6. 重新打开新主档并完成最终验证后才返回成功和更新 UI；
7. 任一步失败，保留最近有效主档和备份，清理或隔离临时文件并返回结构化失败。

如果当前主档是有效 schema `1–30` 且玩家已明确开始新的 3D 进度，先完成第 4.2 节的只读旧档归档，再进入 schema `31` 写入。归档失败则本次 3D 保存失败，旧档保持原位。

### 8.3 加载候选与恢复

候选顺序为有效主档优先、有效备份其次。临时文件不是普通继续候选：

- 主档有效时忽略并清理更旧 `.tmp`；
- 主档无效但备份有效时，从备份加载，在成功恢复场景后隔离损坏主档为 `.corrupt-{timestamp}.json`，并提示“主存档损坏，已恢复备份”；
- 主档和备份都无效时，两者都保留/隔离，拒绝继续；
- 中断恢复标记只由文件系统适配器按明确事务阶段处理，不能根据修改时间猜测并提升任意 `.tmp`；
- 隔离失败时保留原文件并记录诊断，不能因此覆盖它。

从备份成功加载不立即无提示地改写主档。下一次明确保存/检查点通过完整事务生成新主档。所有 I/O、权限、磁盘空间、路径和替换异常都被转换为结果，不穿透到玩家主循环。

### 8.4 迁移和 ID 映射

迁移注册为不可变单向链，例如未来 `31→32`；已发布步骤不得修改。迁移前对原文件创建带 schema 和时间的逐字节备份，备份复读有效后才运行迁移；迁移失败保留原文件和备份。

schema `1–30` 的“旧 2D 兼容默认”与 schema `31+` 的结构迁移是两个明确的链，不得把前者接到 3D payload。官方 ID 改名表集中维护、可回归、单向应用；未知 ID 进入占位/孤立状态而不是被删除。

## 9. 自动检查点与退出

### 9.1 当前垂直切片触发器

自动检查点由已成功提交的领域事件触发，保存同一完整 schema `31` 快照：

| 稳定原因 ID | 触发时机 | 重复策略 |
|---|---|---|
| `new-game-ready` | 新 3D 会话正式初始化和基础表现就绪后 | 每个新进度一次 |
| `first-deployment-complete` | 首次进入 Fortress 且城市/物流同步完成后 | 一次性；对齐 GDD A4.11 首次展开 |
| `first-machine-gun-complete` | 第一座机枪塔完成且教学波已登记后 | 一次性；对齐 GDD A4.11 首座机枪塔 |
| `tutorial-combat-started` | 第一名教学敌人实际生成、战斗状态成立后 | 一次性；预警不算战斗 |
| `evacuation-batch-confirmed` | 撤离确认、载荷捕获和锁全部成功后 | 每批一次 |
| `evacuation-work-committed` | 每个撤离项目原子提交后，含进入容量阻塞的稳定边界 | 每个项目/阻塞转换一次 |
| `packing-complete` | 撤离完成并从 Packing 返回 Mobile 后 | 每次完成一次 |

GDD A4.11 的“开局选择完成”和“Boss 事件开始”在当前正式 3D 垂直切片尚不存在，因此本阶段不伪造事件；相应系统以后正式接入时，必须复用同一检查点命令增加稳定触发器。

系统菜单“保存并退出”不受上述事件限制，始终捕获当前完整状态。正常退出流程只有收到保存成功结果后才退出；失败时停留并显示“保存失败，原存档未被覆盖”，允许重试或由玩家明确选择不保存退出。操作系统强制结束回调只能做尽力请求，不得作为唯一退出保存保证。

### 9.2 合并、抑制和失败

- 同一帧多个事件合并成一个快照，保留确定性最高优先原因和全部已完成里程碑；
- 保存进行中收到新事件时只保留一个“捕获最新状态”的待处理请求，当前事务结束后重新捕获，不复用过期 DTO；
- 加载、回滚、新场景注入和恢复后派生事件期间抑制检查点，防止 load→save 循环；
- 不因生产 tick、资源 UI 刷新或普通移动逐帧写盘；
- 自动检查点失败不停止玩法，但 HUD 保留可见警告直至下一次成功或玩家查看详情；失败不能假装已经保存。

失败重试入口只加载最近有效、与正式 3D 兼容的检查点。没有有效 schema `31` 档时，明确提供重新开始，不调用 2D 档或默认填充恢复。

## 10. 玩家可见结果与错误

统一服务返回稳定结果代码、玩家文案键、可选技术诊断和是否可重试。UI 不解析异常字符串。最少结果包括：

| 结果代码 | 玩家中文说明 |
|---|---|
| `SaveSucceeded` | 游戏已保存 |
| `LoadSucceeded` | 已继续最近进度 |
| `BackupRecovered` | 主存档损坏，已恢复备份 |
| `NoValidSave` | 没有可继续的有效存档 |
| `Legacy2DOnly` | 检测到旧版 2D 存档，不能直接用于当前 3D 游戏 |
| `UnsupportedFutureSchema` | 存档版本过新，请更新游戏后重试 |
| `MissingRequiredContent` | 存档缺少当前版本必需内容，无法安全加载 |
| `RecoverableMissingContent` | 部分内容缺失，已用安全占位保留 |
| `Busy` | 游戏状态正在变化，请稍后再试 |
| `DiskWriteFailed` | 保存失败，原存档未被覆盖 |
| `DiskReadFailed` | 无法读取存档，请检查权限或磁盘 |
| `CorruptNoBackup` | 存档已损坏，且没有可用备份 |
| `RestoreFailedRolledBack` | 加载失败，当前游戏未改变 |
| `RestoreFailedRollbackFailed` | 恢复发生严重错误，请返回标题界面 |

标题“继续”由轻量但完整的档案检查结果驱动，不调用场景 Apply，也不只检查文件存在。阻断错误使用模态对话框；自动检查点失败使用非阻断但持续的 HUD 提示；详细日志包含结果代码和字段路径，但玩家 UI 不暴露本机绝对路径、堆栈或隐私信息。

旧 2D 档说明必须提供“返回”和“开始新的 3D 游戏”选择；后者明确告知会建立新 3D 进度并归档旧档。没有已批准的 2D→3D 转换按钮。

## 11. 程序集与代码所有权

依赖方向保持：

```text
WasteCity.Game
    ↑
WasteCity.Graybox3D
    ↑
WasteCity.Graybox3D.Building
    ↑
WasteCity.Graybox3D.Usability / Editor / Tests
```

### 11.1 `WasteCity.Game`

拥有纯存档合同和唯一基础设施：

- schema `31` envelope/DTO、schema `1–30` 兼容 DTO；
- 分类器、codec、规范编码、哈希、validator、迁移注册表和旧 ID 映射；
- 文件系统/路径适配、原子事务、备份和结构化结果；
- 不依赖 3D MonoBehaviour 的 capture/apply 协议与暂停原因值。

schema `31` DTO只是稳定数据合同，不让 `WasteCity.Game` 引用 `WasteCity.Graybox3D.*` 类型。除唯一文件系统适配器外，纯 codec/validator 测试不读取 `Application`、场景或 UI。

### 11.2 `WasteCity.Graybox3D.Building`

拥有正式 3D capture/restore/checkpoint 编排，因为该程序集已经持有并协调建筑会话、城市仓储、生产、防御和撤离，并可通过显式引用访问城市、世界、背包/合成和研究所有者。它负责：

- 领域 capture/restore 适配器和事务暂停屏障；
- 跨领域预检、应用、回滚和派生状态重建；
- 从正式领域事件发出检查点请求；
- 绝不自行读写文件或生成玩家文案。

Legacy `FormalSaveController` 在过渡期降级为冻结 2D 场景适配器，磁盘和路径职责迁到统一服务；它不能继续成为第二个存档入口。

### 11.3 `WasteCity.Graybox3D.Usability`

拥有标题/系统菜单/失败重试的真实输入接线和 UGUI 展示：

- 发送 New/Continue/SaveAndExit/Retry 命令；
- 消费结构化结果并显示中文；
- 不持有 DTO、文件路径或领域模型，不用直接方法调用绕过正式输入主循环。

### 11.4 Editor、测试与 authoring

Editor authoring 只负责幂等建立明确序列化引用、质量目录和正式场景合同。不得使用 `FindObjectOfType`、对象名称或运行时临时补组件掩盖接线缺失。是否新增独立 persistence asmdef 由实施计划决定；若没有明确依赖收益，优先留在 `WasteCity.Game`，避免循环和同义基础设施。

## 12. 验证合同

实施必须 TDD，最少按下列层次先 RED 后最小实现：

1. schema `31` envelope 往返、稳定排序、哈希、字段默认和语义拒绝；
2. schema `1–30` 固定 fixtures 可读、分类为 2D、绝不静默转 3D；未来 schema 拒绝；
3. 原子临时写、flush 后复读、备份更新、替换失败、权限/磁盘异常和中断恢复；
4. 损坏主档保留、有效备份回退、无效主档不覆盖备份、中文结果；
5. 每个 3D 领域的 capture→扰动→restore，包括未知 ID 和不重复扣料/退款；
6. 活动 Deploying/Packing、活动教学战斗、塔/敌人内部累积量、已确认撤离、活动拆除和容量阻塞；
7. 完整 3D capture→新场景重载→load 的权威指纹一致，以及所有派生网格、物流、状态、路径和 UI 重建；
8. 自动检查点触发、一次性里程碑、合并、加载抑制、保存中再触发和失败重试；
9. 标题、系统菜单和失败提示通过正式 Input System 主循环，不只直接调用内部方法；
10. 稳定 ID/next ordinal 不重用、重复加载幂等、性能与稳定重建。

普通开发运行日常完整 EditMode 和完整 PlayMode；本功能不改地形源贴图、导入规则或数组 Builder，因此不运行 TerrainAssetDeep。完成实现后运行项目质量门、四个正式构建、官方文档生成/验证和 `RecordVerification`。自动化、macOS 构建、用户试玩和真实 Windows 10/11 验收必须分别记录，不能互相冒充。

## 13. 冻结 2D 退役门

退役是 schema `31` 完成后的独立最后阶段，不与首次实现混在同一删除提交。只有以下证据全部成立才可开始：

- schema `31` 全领域往返和新场景重载通过；
- 活动转换、活动战斗、已确认撤离和容量阻塞恢复通过；
- 原子写、损坏主档、备份回退、权限/替换失败通过；
- schema `1–30` 固定 fixtures、类型分类和未来 schema 拒绝通过；
- 自动检查点、保存并退出、失败重试和玩家可见中文错误通过真实输入测试；
- 日常完整 EditMode、完整 PlayMode、项目质量门和四个正式构建通过；
- 最新正式验证文档准确记录未完成的用户试玩和 Windows 实机项，未把它们写成已完成。

退役阶段可以移除：

- `FormalPrototype` 2D 场景及只服务它的场景 bootstrap/controller；
- legacy 2D build 入口和只服务冻结场景的 authoring；
- 已经没有生产引用、且不承担兼容解码的 2D 表现/输入代码。

退役阶段必须保留：

- schema `1–30` 分类器、decoder、冻结迁移/默认规则和固定 fixtures；
- 3D 复用的 `BuildingCatalog`、资源/研究/战斗/城市等纯规则与稳定 ID；
- 统一存档服务、旧 ID 映射和可辨认旧档的玩家说明；
- 历史归档读取/诊断能力。

删除前必须进行生产引用扫描、场景/build settings 合同检查和共享程序集审查。若某个旧控制器仍是 schema `1–30` 语义的唯一可执行参考，应先把其兼容规则转成受 fixture 保护的纯兼容适配，再删除场景控制器。退役后默认 build settings 不再包含 2D 场景，也不再提供 legacy 2D build 菜单；这不等于删除历史档案识别能力。

## 14. 关键决策摘要

1. schema `31` 是带 `runtimeKind = formal-3d` 的独立 payload，不扩写 schema `30`。
2. 全项目只有一个逻辑槽、一个文件事务、一个分类/迁移入口和一套结果代码。
3. 保存领域权威事实和隐藏模拟累积量；物流、停工原因、目标和 UI 全部重建。
