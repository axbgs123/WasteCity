# 项目测试、可复用目录与文档自动维护设计规格

> 日期：2026-08-12<br>
> 状态：书面规格已获用户批准，工具尚未实现<br>
> 受控需求：`DOC-0001`<br>
> 适用范围：整个 WasteCity 仓库及后续所有功能、美术接入、场景、UI、测试与 Bug 修复<br>
> 当前分支基线：`codex/playtest-fixes`<br>
> 关联文档：`AGENTS.md`、`README.md`、`Docs/05-Formal-Development-Roadmap-ZH.md`、`Docs/06-User-Feedback-and-Change-Control-ZH.md`

## 1. 目的

本变更建立一套面向整个项目的长期开发规范，解决三个问题：

1. 项目已经拥有大量自动测试，但缺少按功能整理的入口，失败后仍需要人工猜测应检查哪个系统；
2. 代码、组件、场景、UI 和美术接入中已有许多可以复用的内容，但目前没有统一目录，新开发者容易重复造轮子或错误复用冻结的 2D 占位实现；
3. README、测试数量、功能状态和文件目录依靠人工更新，随着项目快速变化容易过期。

目标不是增加一份很长但很快失真的手写名单，而是建立：

- 给用户和新开发者阅读的普通中文说明；
- 给开发者和 AI 使用的精确技术目录；
- 由工具生成的文件、测试和验证快照；
- 能把测试失败快速映射到功能、组件、场景和需求编号的定位报告；
- 后续每项开发完成前必须通过的文档与测试检查门。

设计阶段只记录可验证的当前事实，不把计划描述为已实现：

- `Assets/_Game/Tests/EditMode` 当前有 `93` 个 C# 测试文件；

- 静态扫描当前约有 `1117` 个 NUnit/Unity Test 测试声明；实际执行数量以最新测试 XML 为准；
- 当前启用场景为默认 3D `GrayboxPrototype3D` 和冻结 2D `FormalPrototype`；
- 当前有游戏规则、3D 基础、3D 建造、美术接入、Editor、EditMode 测试和 PlayMode 测试共 `7` 个程序集定义；
- 当前完整回归基线为 EditMode `1121/1121`、PlayMode `82/82`；
- 当前 README 仍显示更早的 `492/492`、`58/58` 基线，证明人工维护已经发生明显漂移；

## 3. 已批准原则

### 3.1 面向用户的文档必须易读

- 主文档先说明“这是什么、怎么用、出问题看哪里”；
- 不假设读者具有计算机或 Unity 背景；
- 必须出现技术名称时，先用普通中文解释，再在括号中附代码名；
- 不用缩写代替解释；首次出现 `EditMode`、`PlayMode`、程序集、组件等词时必须给出一句中文说明；
- 主文档不得直接堆放全部类名、测试方法名或序列化字段；这些内容放入自动生成的技术附录。

示例：

```text
城市移动控制：负责城市手动驾驶、自动寻路和展开状态下的移动限制。
代码名：GrayboxMobileCityController3D
```

### 3.2 自动更新只处理客观事实

自动工具可以更新：

- 文件、组件、程序集、场景和 UI 清单；
- 测试文件、测试组、最新执行数量和结果；
- 构建入口、默认场景和已存在的路径；
- 可复用条目的路径存在性与关联测试；
- 当前提交、生成时间和验证命令。

自动工具不得直接改写：

- 主 GDD 的玩法规则；
- 用户反馈的原始描述；
- `BUG/IDEA/DOC` 的审批状态和人工验收结论；
- “功能已经实现”“已经验证”等需要人类判断的语义；
- 路线图完成百分比。

原因是文件变化不能可靠推断产品含义。工具应生成“需要人工确认的文档提醒”，而不是猜测后自动改变玩法事实。

### 3.3 不是所有代码都允许复用

自动文件清单和“推荐复用目录”必须分开：

- 自动文件清单记录项目中真实存在的全部对象；
- 推荐复用目录只收录职责清楚、接口稳定且有测试保护的内容；
- 冻结 2D、临时占位、场景专用组件和内部实现必须明确标记，避免后续开发者把它们当成通用模板；
- “可找到”不等于“可复用”。

## 4. 文档结构

### 4.1 用户和新开发者入口

新增 `Docs/07-Project-Use-and-Development-Guide-ZH.md`，使用普通中文维护：

- 项目现在能做什么、尚不能做什么；
- 怎样打开、运行和构建默认 3D 版本；
- 两个场景分别有什么用途；
- 主要按键、界面和开发修改器入口；
- 修改地图、城市、建造、研究、美术或 UI 时应先看哪里；
- 常见问题和最短检查路径；
- 指向测试指南、复用目录和受控需求文档的链接。

该文档不复制完整 GDD，也不承诺未实现功能。

### 4.2 测试与 Bug 定位指南

新增 `Docs/08-Testing-and-Bug-Location-Guide-ZH.md`，使用普通中文维护：

- 四层测试的区别与使用时机；
- 怎样只检查一个功能；
- 怎样查看失败定位报告；
- 玩家试玩 Bug 应记录哪些信息；
- Bug 从复现到验证的标准流程；
- 偶发测试、环境失败和真实功能回归如何区分；
- 哪些修改必须运行真实场景、完整回归或 Windows 构建。

### 4.3 推荐复用目录

新增 `Docs/09-Reusable-Project-Catalog-ZH.md`。每项条目采用固定、易读格式：

| 字段 | 含义 |
|---|---|
| 普通名称 | 先用中文说明它解决什么问题 |
| 代码或资源名称 | 精确类名、Prefab、场景、材质或文件名 |
| 路径 | 仓库中的相对路径 |
| 类型 | 规则、数据、场景连接、界面、表现、美术、Editor 工具等 |
| 推荐程度 | 推荐复用、复用前审查、仅当前场景、冻结保留、禁止新功能使用 |
| 怎样使用 | 最小接入方式和必要依赖 |
| 不能负责什么 | 防止把玩法真值塞进 UI、美术或 Collider |
| 关联场景/UI | 使用该内容的位置 |
| 关联测试组 | 修改后必须运行的快速测试组 |
| 关联需求 | `BUG/IDEA/DOC` 稳定编号 |

首版至少覆盖：

- 稳定 ID 与内容目录；
- 地图、二维逻辑坐标与 XZ 表现映射；
- 城市寻路、地形、展开和直接控制规则；
- 建筑目录、网格、解锁、施工、退款、撤离和双网格适配；
- 输入优先级、相机、UGUI 建造界面和开发修改器；
- `VisualSlot`、地形表现、共享材质和美术回退；
- 存档、时钟、资源、研究、人口、战斗和路线模型；
- Editor 场景生成、构建工具和性能探针；
- 默认 3D 场景与冻结 2D 场景；
- 明确不可作为新 3D 基础复用的 Placeholder/Frozen 路径。

### 4.4 自动生成的技术附录

新增 `Docs/Generated/`，至少生成：

- `Project-Inventory-ZH.md`：程序集、生产代码、组件、ScriptableObject、场景、UI、Editor 工具和美术接入文件；
- `Test-Inventory-ZH.md`：测试组、测试文件、测试类、关联功能和推荐过滤器；
- `Latest-Verification-ZH.md`：最新已登记的 EditMode、PlayMode、编译、构建和人工验收结果；
- `Documentation-Attention-ZH.md`：当前代码变化可能需要人工检查的 GDD、路线图或受控需求列表。

所有生成文件顶部必须写明“由工具生成，请勿手改”。三个结构目录记录生成工具版本和确定性内容指纹，不写每次都会变化的当前时间或当前提交；相同输入必须逐字节生成相同文件。只有 `Latest-Verification-ZH.md` 记录明确传入的被验证提交 SHA、验证时间和结果路径；这些值属于一次真实验证的输入，而不是工具擅自读取并不断变化的环境信息。

## 5. 单一登记源

新增一个机器可读的项目质量目录，例如：

`Docs/Engineering/project-quality-catalog.json`

它只保存工具无法从源码可靠推断的关系：

- 功能组 ID 和普通中文名称；
- 负责的源代码路径规则；
- 推荐复用条目及其等级；
- 测试类到功能组的映射；
- 场景与 UI 入口；
- 关联 `BUG/IDEA/DOC`；
- 修改后需要的最低验证层级；
- 需要人工检查的正式文档。

文件、类型和测试是否真实存在由工具扫描，不在 JSON 中重复复制能够自动发现的事实。

首版功能组固定为：

1. 项目基础与时钟；
2. 世界地图与地形；
3. 城市移动、寻路与展开；
4. 领袖与直接控制；
5. 建造、施工与撤离；
6. UI 与输入；
7. 资源、生产与物流；
8. 研究与人口；
9. 战斗、敌人和路线能力；
10. 存档与迁移；
11. 3D 表现与正式地表；
12. 场景、Editor、构建与性能；
13. 冻结 2D 回归。

每个生产 C# 文件必须至少属于一个功能组，或明确登记为“暂不归类并说明原因”。新增未归类文件时，质量检查失败并显示缺失路径。

## 6. 测试分层

### 6.1 快速规则检查

用于无场景依赖的模型和规则，例如地图、库存、建筑合法性、退款和研究条件。

- 优先使用普通 NUnit EditMode 测试；
- 不创建不必要的 GameObject；
- 一个失败应尽量只说明一条规则；
- 测试名称采用“条件_操作_预期结果”的可读结构；
- 断言消息必须包含关键输入和预期/实际值。

### 6.2 单功能检查

一个功能组可以包含多个测试类。生成目录为每组给出可复制的 Unity `-testFilter`，使开发者不必运行全部一千多项测试。

单功能测试失败时，定位报告必须列出：

- 功能组普通中文名称；
- 失败测试完整名称；
- 责任源文件和测试文件；
- 相关场景或 UI；
- 关联需求编号；
- 推荐下一条隔离复跑命令。

### 6.3 真实场景检查

涉及输入、UGUI、序列化引用、生命周期、物理提交、场景对象树或场景作用域 URP 时，必须使用 PlayMode 或场景合同测试。

真实输入测试不得通过直接调用最终控制器方法来冒充玩家操作。应使用虚拟键盘/鼠标，经 Input System 和真实 `Update/FixedUpdate/LateUpdate` 调用链验证。

### 6.4 完整回归与构建

交付前根据变更风险运行：

- 完整 EditMode；
- 完整 PlayMode；
- 无界面编译；
- 默认 Release 3D Windows 构建；
- Development 3D 构建；
- 冻结 legacy 2D 构建；
- 必要的性能与真实 Windows 冒烟。

目录中的每个功能组记录最低门，但开发者可以因影响范围扩大验证，不得缩小已批准门槛。

### 6.5 人工试玩

人工试玩是第五层验收，不属于单元测试：

- 自动测试通过不等于画面、手感或说明已经让用户满意；
- 用户计划于次日进行的试玩只登记真实发现，不预先标记为通过；
- 新 Bug 继续先按 `Docs/06` 澄清、编号和批准；
- 能自动化复现的 Bug 必须补回归测试；纯视觉或体验问题可以使用固定截图、参数证据和人工复验。

## 7. 快速 Bug 定位

### 7.1 失败定位报告

新增 Editor 工具读取 Unity NUnit XML，并生成普通中文报告。报告格式固定为：

```text
问题区域：建造与施工
失败位置：研究站 / 移动城市内城放置
失败测试：完整测试名称
优先检查：建筑定义、移动建造规则、放置会话
相关文件：精确相对路径
相关场景：GrayboxPrototype3D
相关需求：IDEA-0005
建议复跑：只运行“建造与施工”组
原始错误：NUnit 原始错误与堆栈
```

工具只提供定位线索，不自动判断根因，也不自动修改代码。

### 7.2 Bug 修复闭环

每个 Bug 依次经过：

1. 保留用户原始描述；
2. 在正确环境复现；
3. 写出能稳定失败的最小测试；
4. 证明失败来自目标行为而不是夹具或环境；
5. 做最小修复；
6. 运行单功能测试；
7. 运行相邻功能测试；
8. 按风险运行完整回归、编译和构建；
9. 自动更新文件与测试技术附录；
10. 人工更新受控状态和验证结论；
11. 等待用户试玩的问题不得提前标记为“已验证”。

### 7.3 偶发失败

偶发失败不得直接忽略：

- 先单项复现；
- 再在相同进程和完整测试中复跑；
- 判断是产品状态、测试夹具、帧边界还是环境问题；
- 测试夹具问题同样需要修复和记录；
- 只有具有零相关代码差异、隔离复现通过和完整复跑通过的既有波动，才可作为非回归证据记录；
- 不允许通过无限重试掩盖真实失败。

## 8. 自动更新与检查门

### 8.1 Editor 工具

新增 `WasteCity.Editor.ProjectQualityTools`，提供菜单和无界面入口：

- `GenerateDocumentation`：扫描并更新技术附录；
- `ValidateDocumentation`：只读检查目录、路径、映射和生成文件是否过期；
- `AnalyzeTestResults`：读取测试 XML 并生成失败定位报告；
- `RecordVerification`：从明确传入的测试结果和构建结果生成最新验证快照。

验证命令不得在检查过程中悄悄改文件。生成和验证必须是两个独立入口。

### 8.2 完成任务前的强制顺序

以后每项开发完成前必须：

1. 读取 `Docs/06` 并引用稳定需求 ID；
2. 将新增或改变的文件归入功能组；
3. 更新推荐复用目录中的新增公共能力或复用限制；
4. 补充或更新对应测试；
5. 运行快速或真实场景测试；
6. 运行文档生成工具；
7. 运行文档只读验证；
8. 按风险完成完整回归、编译、构建和性能检查；
9. 人工确认需要改变的 GDD、路线图和 `Docs/06` 状态；
10. 精确暂存任务文件，保留用户和其它工具的未提交修改。

`AGENTS.md` 必须把这套顺序加入开发完成门。README 和 `Docs/README.md` 必须链接三个主文档。

### 8.3 变化与文档提醒

工具根据变更路径和功能组生成提醒，例如：

- 改建筑规则：检查 GDD 建筑规则、路线图、建造测试和复用目录；
- 改场景或 authoring：检查场景合同、幂等性、GUID 和构建入口；
- 改 UI/输入：检查真实虚拟输入、焦点不穿透和默认场景；
- 改存档：检查 schema、迁移、旧档回归和备份；
- 改正式美术：检查资产记录、许可证、LFS、Importer、灰盒回退和性能。

提醒没有被人工确认时，工具不得自行写“已实现”或“已验证”。

## 9. 命名与职责规范

现有文件不为统一外观而批量重命名；新文件遵循：

- `*Model`：保存纯状态；
- `*Rules`：无场景依赖的规则判断；
- `*Controller`：推进运行时流程；
- `*View`：只负责显示和用户可见反馈；
- `*Presenter`：把模型数据转换为显示数据；
- `*Router`：按优先级分发输入或请求；
- `*Bootstrap`：只负责组合依赖和启动；
- `*Authoring`：只负责 Editor 中创建或更新资产/场景；
- `*Tests`：测试类；
- C# 文件名应与主要 public 类型一致。

职责边界：

- UI 和美术不得保存玩法真值；
- Collider 不得替代地图、占格或通行规则；
- Bootstrap 不得复制业务规则；
- 3D 适配层优先复用 `WasteCity.Game` 的纯规则；
- 冻结 2D 控制器只用于回归，不作为新 3D 功能模板；
- 稳定 ID 发布后不得随显示名称改变；
- 场景序列化引用必须有场景合同或 PlayMode 覆盖；
- 任何公共复用入口必须有成功、失败和生命周期测试。

## 10. 目录完整性规则

质量检查至少验证：

- 所有登记路径真实存在；
- 不存在重复功能组 ID、复用条目 ID 或场景 ID；
- 所有生产 C# 文件已归类或有明确排除原因；
- 所有测试类至少属于一个功能组；
- 所有启用 Build Settings 场景都在场景目录中；
- 默认 3D 与冻结 2D 的用途不会互换；
- 推荐复用条目至少关联一个测试组；
- UI 条目明确 Canvas、EventSystem、输入优先级和场景归属；
- 美术条目明确稳定槽、源文件、Unity 资产、回退和玩法真值边界；
- 生成文档与当前扫描结果一致；
- 手工文档中的关键链接有效；
- 未提交的用户或 MCP 文件不会被生成工具暂存、删除或覆盖。

## 11. 工具自身测试

新增 EditMode 测试覆盖：

- 目录 JSON 可解析且字段完整；
- 重复 ID、缺失路径、未归类代码和未归类测试会给出精确错误；
- 两次生成输出主体逐字节一致；
- 普通结构目录不写当前时间或自动读取当前 Git SHA；最新验证快照只使用调用方明确传入的被验证提交与时间；
- 场景、程序集、MonoBehaviour、ScriptableObject 和测试发现结果正确；
- 冻结 2D 条目不能被标为推荐的新 3D 基础；
- 示例 NUnit XML 能映射到正确功能组、源文件和复跑建议；
- 未知测试得到“未归类”明确错误，而不是静默丢失；
- 验证入口不写文件；
- 生成入口只修改批准的 Docs/Generated 路径；
- 当前工作区的外部未提交文件保持字节不变。

首轮不批量重写全部既有测试。只有在目录检查发现无法稳定归类、断言缺少关键信息或测试本身不稳定时，才以独立任务逐步加固。

## 12. 错误处理

- 缺失目录文件：验证失败并显示精确路径；
- JSON 语法错误：显示行列和字段，不生成半份文档；
- 发现未知生产文件或测试：列入“未归类”并使完成门失败；
- 生成中断：先写临时文件，全部成功后再替换目标，避免破坏已有文档；
- 测试 XML 不完整：保留原始 XML，报告“结果不完整”，不得写成通过；
- 同一测试映射到多个冲突功能组：验证失败，要求明确主组和相关组；
- 场景无法加载或含 Missing Script：验证失败，不从目录中隐藏；
- 自动工具遇到 GDD/需求语义变化：只产生提醒并停止自动语义更新。

## 13. 不包含的范围

本里程碑不包含：

- 修改任何游戏玩法、数值、场景内容或正式美术；
- 修复明天尚未出现的试玩 Bug；
- 为提高覆盖率数字而批量编写低价值测试；
- 批量重命名现有类、文件或测试；
- 引入付费测试平台、外部数据库或新的云服务；
- 在 GitHub Actions 中配置 Unity 许可证；
- 自动批准用户需求、自动改变 GDD 或自动宣称人工验收通过；
- 清理当前工作区中用户或 Unity/MCP 产生的未提交文件。

云端 CI 可以在未来需要多人协作和候选发布时单独设计。当前优先使用仓库内、跨电脑可复现的 Unity Editor 工具和测试。

## 14. 实施顺序

1. 登记 `DOC-0001` 并冻结本规格；
2. 建立机器可读目录格式与解析器；
3. 为现有生产文件、测试、场景和 UI 建立首版分类；
4. 实现确定性项目扫描和生成器；
5. 实现只读目录验证；
6. 实现 NUnit XML 失败定位报告；
7. 编写三个普通中文主文档；

9. 更新 `AGENTS.md`、README 和 Docs 索引；
10. 运行工具自身测试、完整 EditMode/PlayMode 和无界面编译；

## 15. 验收条件

完成时必须同时满足：

- 三份主文档可由非计算机背景用户理解；
- 自动技术附录覆盖当前生产代码、测试、场景、UI、Editor 工具和关键美术接入；
- 所有生产 C# 文件和测试类均已归类或有明确排除原因；
- 推荐复用目录明确区分推荐、有限、场景专用、冻结和禁止新用；
- 可以从任意失败测试得到功能组、相关文件、场景、需求 ID 和复跑建议；
- 生成器两次运行结果稳定；
- 只读验证能发现过期目录、缺失文件和未归类新增内容；
- `AGENTS.md` 把测试与文档更新列为以后每项任务的完成门；
- README、Docs 索引与当前测试/入口事实一致；
- 完整 EditMode、PlayMode 和无界面编译通过；
- 默认 3D、冻结 2D、存档 schema、Packages、Graphics/Quality 设置和正式游戏逻辑保持零差异；
- 当前受保护的地形 `.meta` 和本机 ProjectSettings 改动未被暂存、覆盖或清理；
- `DOC-0001` 在机器实现完成前不得标为“已验证”；
- 用户明天的试玩结果另行登记，不预先推断。

## 16. 回退

所有新增能力限定在文档、Editor 质量工具、机器目录和测试中。若工具不可用：

- 游戏运行时、场景和存档不受影响；
- 删除新增质量工具与生成目录即可回退；
- 三份普通中文文档仍可保留为人工参考；
- 不允许为了让目录工具工作而改变游戏规则或场景真值。
