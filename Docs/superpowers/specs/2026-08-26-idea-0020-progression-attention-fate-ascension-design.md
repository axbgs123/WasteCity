**日期：** 2026-08-26

**正式存档版本：** schema `33`

## 1. 目标与权威边界

本阶段为正式 3D 主循环补齐“风险随发展累积、玩家选择一条命轨、完成首轮文明升阶”的可玩闭环：

```text
建造 / 研究 / 战斗 / 命轨行为
              ↓
       关注度 0—100
              ↓
   30 / 60 / 90 压力事件队列
              ↓
遗产解析 + 防御准备 + Boss + 生产运行
              ↓
       文明等级 1 → 2
              ↓
       已选命轨 Lv.1 → Lv.2
```

本规格只适用于正式 3D。schema `1—30` 的冻结 2D 存档、规则和 `RewindAnchorRules` 必须保持原样，不接入新功能。

本文与既有文档出现歧义时，采用以下已批准决定：

1. 首次会话固定展示三条命轨，不从长期设计中的 24 条命轨随机抽取；玩家只选一条。
2. 选中命轨立即为 Lv.1，首次文明升阶后变为 Lv.2，不采用 B 卷中“首次部署即 Lv.2、首次升阶即 Lv.3”的长期节奏。
3. 正式 3D 回溯锚点每次读取增加关注度 `12`，以 GDD A16 为准；冻结 2D 的 `+3` 不变。
4. 首次升阶必须同时满足 GDD A4.9 的四个条件，不采用隐藏条件或任一条件即可升阶的解释。
5. `core.research.legacy-analysis` 从预览节点变成可研究节点，正式科技总数从 IDEA-0016 的 43 个变为 44 个；这是 IDEA-0020 对旧数量的明确后续修订。
6. IDEA-0017 的十波战役保持完整，不改波次、敌人、结算或胜负规则；关注度压力事件使用独立串行队列，不能与战役波次或另一场压力事件重叠。

## 2. 数据与运行时所有权

### 2.1 三套真值

| 真值 | 唯一所有者 | 不得承担的职责 |
|---|---|---|
| 静态定义 | `FormalProgressionCatalog`、`AttentionSourceCatalog`、`AttentionEncounterCatalog`、既有建筑/资源/科技目录 | 不保存会话状态，不读取场景对象 |
| 会话状态 | `FormalProgressionRuntime3D` | 不持有 GameObject、UI 文本、贴图或输入绑定 |
| 存档状态 | `FormalThreeDSaveData.Progression` 与内部回溯锚点封装 | 不自行推进时间，不作为第二套运行时模型 |

`FormalProgressionRuntime3D` 唯一拥有：文明等级、关注度、关注度历史、阈值锁存、命轨选择及等级、命轨专属状态、压力事件队列、Boss 击败状态和升阶序列状态。UI 只能读取不可变快照并提交命令，不得直接改字段。

既有系统继续拥有其领域真值：

- 建筑实例、完成/归属/摧毁状态：统一建筑系统；
- 建造成本和原子资源交易：统一资源账本与建造事务；
- 生产是否可运行：正式生产运行时；
- 研究解锁、计时和成本：正式科技运行时；
- 敌人生命、波次和伤害：既有战斗运行时；
- 资源节点、地形和占用：`WorldMapModel`；
- 规则时间和暂停：统一规则时钟。

关注度系统只订阅这些系统成功提交后的领域事件，不重新判断放置、库存、研究完成、生产资格或击杀。表现层事件、按钮点击和动画结束都不能成为规则真值。

### 2.2 建议运行时组成

- `FormalProgressionRuntime3D`：事务入口、状态快照、revision 和存档适配；
- `AttentionLedger`：幂等变更、历史、阈值检测；
- `FateRuntime`：三命轨的统一接口与专属小状态；
- `AttentionEncounterQueue`：阈值遭遇的排队、启动、完成和恢复；
- `CivilizationAscensionCoordinator`：资格检查与原子升阶；
- `ProgressionDomainEventRouter`：把既有领域事件映射成稳定关注度事件；
- `FormalProgressionSaveAdapter`：schema 33 DTO、迁移、验证和原子读写；
- `ProgressionHudPresenter3D`：快照到 UI 的单向投影；
- `ProgressionInputCoordinator3D`：Input System 动作到领域命令。

不得建立第二份玩家资源账本、第二套研究图、第二套敌人生命或每帧扫描场景来推断状态。

## 4. 关注度账本与事件幂等

### 4.1 数值和显示

- 范围固定为 `0—100`，新会话为 `10`。
- 语义区间：`0—29 未锁定`、`30—59 异常回波`、`60—89 定向观测`、`90—100 坐标锁定`。
- 每条历史记录保存：稳定事件 ID、来源 ID、原因显示键、请求变化量、夹取后的实际变化量、变化后数值、规则时间和可选来源实例 ID。
- 完整运行历史采用容量 `128` 的 FIFO 环形记录；HUD 最近原因只投影最后 3 条。幂等提交 ID 另存，不能因历史淘汰而允许一次性事件重放。
- 夹取导致实际变化为 0 时仍可记录已提交事件，防止同一一次性奖励在数值下降后重放。

### 4.2 提交合同

统一入口为概念上的 `TryApplyAttention(command)`：

1. 验证来源 ID、事件 ID、变化规则和当前状态；
2. 对一次性事件检查 `CommittedEventIds`；
3. 在临时状态上计算数值、历史和按升序跨越的阈值；
4. 为新跨越阈值追加遭遇队列项；
5. 一次提交数值、历史、幂等 ID、阈值锁存和队列；
6. revision 只增加一次，再发布领域事件。

任何一步失败都不改变运行时。订阅者异常不能回滚已成功提交的规则状态，但必须隔离并记录错误。

一次性事件 ID 必须由稳定语义组成，例如研究使用研究 ID、首座建筑使用建筑定义 ID、每座机枪塔使用稳定建筑实例 ID。虚空债是可重复事件，使用保存的债务结算序号生成 `source-id:cycle-ordinal`，加载后不能重算已经结算的周期。

阈值每个存档只锁存一次。关注度降低不会清除锁存，也不会取消已排队遭遇；降低只影响尚未生成的增援或后续配置读取。一次变化跨过多个阈值时，按 `30 → 60 → 90` 排队。

## 5. 三条固定命轨

### 5.1 选择流程

schema 33 新会话和由 schema 32 迁移且尚未选择命轨的存档，在进入可操作世界前显示强制选择面板。面板固定展示三项中文名、简介、Lv.1 效果、Lv.2 预览与代价。系统菜单仍可打开，但建造、相机、战斗和快捷键不能穿透。

确认仅可成功一次，并在同一事务内：保存选中 ID、设置命轨 Lv.1、增加关注度 5、锁存相应阈值、生成检查点 `fate-selection-complete`。关闭或重载不能重新抽取或重复加关注度。

### 5.2 袖珍宇宙

“每一类生产建筑”按正式机器配方目录引用的稳定建筑定义 ID 区分，不通过组件、显示名称或场景对象猜测，也不维护第二份平行清单。所有至少拥有一条正式机器配方的生产建筑类型都参与；手工合成配方不产生旗舰。

Lv.1：

- 每个合格建筑类型，首个完成且归玩家所有的实例成为该类型永久旗舰；保存稳定实例 ID。
- 旗舰每次完整生产提交的输出数量乘 `2`；输入、周期、物流和缓存容量不变，仍要求完整产物可写入。
- 任一旗舰在本存档首次真实完成生产时，全局只增加一次关注度 `4`；事件 ID 同时记录命轨 ID 与首个旗舰实例 ID，其他类别旗舰以后启动不重复增加。
- 旗舰被摧毁时，通过统一建筑摧毁事件生成以其占地中心为基准的 `3×3` 坍缩规则区域；伤害和占用效果进入领域模型，不能只播放特效。
- 当前里程碑不转移旗舰资格；重建同类建筑不会再次获得加成。

Lv.2：输出倍率变为 `4`，坍缩区域变为 `4×4`；旗舰 ID、首产事件和不转移规则保持不变。

倍增在生产产物写入前计算；若完整倍增产物放不下，本周期停在完成边界，不截断、不丢失、不重复扣输入。

### 5.3 虚空债

Lv.1：

- 只有建筑施工成本可让对应城市资源降到负数；生产、研究、背包合成、人工转移和其他消费仍要求实有资源。
- 负数库存即对应资源债务，不建立第二份虚构货币。其绝对值计入总未偿债务。
- 后续同资源收入先偿还负数，再形成可用正数；所有操作经过统一资源事务。
- 每 `30` 秒规则时间结算一次；全局暂停冻结计时。每完整 `10` 点总未偿债务增加关注度 `1`，余数不进位。债务为 `1—9` 时本周期不增加。
- 存档保存各资源负余额、当前结算计时和下一个结算序号。HUD 显示总债务、分资源债务、距下次结算时间及预计关注度。

Lv.2：结算间隔延长为 `60` 秒；每完整 `10` 点债务增加 `1` 的规则、施工限定和自动偿还规则不变。

建造预览必须同时显示实付与新增债务。建造失败或取消不能留下负余额；建筑成功提交和负余额是同一原子事务。

### 5.4 回溯锚点

Lv.1 可保存 1 个锚点；创建新锚点原子替换旧锚点。Lv.2 可保存 2 个锚点，按稳定创建序号排列；已满后创建第三个时原子替换最旧项。

锚点是内部世界快照，不是新增玩家存档槽。主存档只保存锚点元数据、稳定内部键、创建序号和内容摘要；载荷由现有正式存档编解码、验证和原子文件存储写入专用内部封装。锚点载荷不得递归包含锚点载荷本身。

创建和读取锚点在以下状态禁止：活动战斗、部署或收拢事务中、已确认撤离流程中、另一个存档事务中。UI 显示具体阻止原因。

读取顺序：

1. 只读解码并完整验证目标锚点；
2. 捕获当前可回滚运行时快照和当前关注度/阈值锁存；
3. 通过统一加载协调器恢复锚点世界；
4. 覆盖恢复前保存的当前关注度与阈值锁存，再原子增加 `12`；
5. 提交运行时、压力队列和正式检查点；
6. 任一适配器失败时恢复第 2 步快照，目标锚点和主存档均不改写。

因此建筑、库存、科技、战斗和世界状态回到锚点；关注度、已触发阈值及其压力队列不会被回退。每次成功读取都增加 12，失败读取不增加。schema `1—30` 的旧 2D 回溯 `+3` 永不迁移到本规则。

## 6. 30 / 60 / 90 压力事件

### 6.1 调度

- 首次到达 30：排队定向攻击；在教学波结束且首座机枪塔完成后，给出 60 秒警告再启动。
- 首次到达 60：排队高风险攻击；必须等待定向攻击完成，再给出 75 秒警告。
- 首次到达 90：排队晶壳母体；必须等待高风险攻击完成，再给出 90 秒警告。
- IDEA-0017 十波战役优先保持当前运行；其活动期间压力事件只排队。战役完成进入继续游戏沙盒后，压力队列按阈值升序逐一执行。
- 同一时刻只允许一场战役/压力遭遇拥有刷怪权。保存并恢复 queued、warning、active、completed 状态和剩余警告规则时间。

### 6.2 正式组成

| 遭遇 | 组成 |
|---|---|
| 定向攻击 | 18 啃噬者、4 晶壳兽，从 2 个方向进入 |
| 高风险攻击 | 24 啃噬者、6 晶壳兽、4 啸叫者、1 结晶掘地者 |
| 晶壳母体 | 1 晶壳母体及阶段增援 |

晶壳母体首版为非建模占位：`4000` 生命、移动速度 `0.6` 格/秒，使用清晰可替换的程序化几何、独立轮廓色、世界血条和阶段标记。真值仍在敌人模型，不以 Transform 大小或颜色判断阶段。

Boss 使用两个配置化阶段阈值：70% 生命时增援 4 晶壳兽；35% 生命时增援 6 啃噬者和 2 啸叫者。阶段事件以 Boss 稳定实例 ID 与阶段 ID 幂等，保存后不重复生成。结晶掘地者和 Boss 在缺少正式模型时均使用清晰占位表现，不因此扩大建模范围。

Boss 正式击败事件设置 `BossDefeated=true` 并成为升阶条件；只有统一战斗运行时确认死亡才可提交。降低关注度不会复活、取消或重复 Boss。

## 8. 首次文明升阶

### 8.1 四个同时满足的条件

1. `core.research.legacy-analysis` 已完成；
2. 当前至少有 2 座已完成、归玩家所有且未被摧毁的机枪塔；
3. 晶壳母体已被正式战斗运行时确认击败；
4. 当前至少有 1 座已完成生产建筑可开始或继续一个正式生产周期。

第四项复用生产运行时的统一资格查询；内部有产出但已暂停、枯竭、满仓或无输入的建筑不算“正在运行”。条件面板实时显示四项状态和具体未满足原因。

### 8.2 真实输入与原子顺序

默认 Input System 动作为 `U`。只有四项全满足、文明等级为 1、没有更高优先级模态框/搜索输入、且没有正在提交的升阶时才接受。按钮点击和 `U` 必须走同一公共命令。

一次成功升阶在临时状态中按以下确定顺序组装并一次提交：

1. 再验证四项条件及所有稳定引用；
2. 文明等级 `1 → 2`；
3. 已选命轨 `Lv.1 → Lv.2`，立即应用第 5 节参数；
4. 关注度增加 `25`，按规则锁存并排队新跨越阈值；
5. 启动可恢复的升阶演出序列；
6. 写入 `first-civilization-ascension` 正式检查点。

任何规则提交失败都不改变等级、命轨、关注度或检查点。演出阶段保存为 `requested / fate-upgraded / attention-pulse / scan / completed` 及剩余规则时间；中途保存加载从该阶段继续，但不能重复规则奖励。演出失败只降级为无动画完成，不回滚已经成功的领域事务。

本阶段只支持 1→2，一旦完成不能再次触发。后续文明等级没有配置时 UI 显示“后续升阶尚未开放”。

## 9. schema 33

### 9.1 DTO

`FormalThreeDSaveData` 增加 `Progression`，至少保存：

- `CivilizationLevel`；
- `AttentionValue`；
- `TriggeredThresholdIds`；
- 结构化关注度历史与 `CommittedEventIds`；
- 固定 offered 命轨 ID、selected ID、fate level；
- 袖珍宇宙各类型旗舰实例 ID 和首产提交 ID；
- 虚空债各资源负余额、结算剩余时间和下个周期序号；
- 回溯锚点元数据列表、稳定内部键和创建序号；
- queued / warning / active 压力遭遇、剩余时间和已提交阶段；
- Boss defeated；
- 升阶序列阶段、剩余时间及完成锁存；
- `ConfigurationSignature`。

所有集合保存稳定排序；未知重复 ID、越界数值、互斥遭遇状态、无效命轨等级、悬空锚点引用和不可能的文明等级必须由 validator 拒绝，不能静默猜测。

### 9.2 迁移与兼容

- 正式加载链为 schema `31 → 32 → 33`，不得跳过已有迁移器。
- schema 32 迁到 33：文明等级 1、关注度 10、阈值为空、命轨待选择且 level 0、无旗舰、无债务、无锚点、无压力遭遇、Boss 未击败、升阶未开始。
- 不从旧建筑、科技或战斗历史反推关注度，避免同一旧存档因实现版本不同得到不同结果。
- schema 33 首次选择命轨后才进入 level 1。
- schema `1—30` 的冻结 2D 数据、迁移和历史语义不变；正式 3D schema 33 不覆盖或重写旧文件。
- 主存档写入继续使用临时文件、验证、原子替换和失败保留旧文件的合同。内部锚点也遵守同一合同。

## 10. HUD、面板与真实输入

### 10.1 常驻 HUD

在现有资源状态栏的清晰边缘位置增加关注度模块，不挤压资源数字或改变世界比例：

- 当前值 `x/100`；
- 当前语义状态；
- 下一阈值及距离；
- 最近一条原因与 `+/-` 变化；
- 有压力事件时显示等待、警告或进行中状态。

点击模块或正式 Input Action 打开详情，显示最近 3 条原因、完整可滚动历史、阈值状态和排队遭遇。UI 使用目录显示键，不把代码枚举名暴露给玩家。

### 10.2 命轨与升阶面板

- 命轨选择是一次性阻塞模态框，三卡均展示 Lv.1、Lv.2 和明确代价；需二次确认。
- 选择后详情页显示已选命轨、等级、专属状态：旗舰、债务/计时或锚点槽。
- 升阶页显示四项检查清单、文明等级、命轨升级预览、关注度 +25 和 `U` 提示。
- 不能只用颜色表达可用、警告或失败；必须有图标/文本和可读焦点状态。
- 失败提示固定在相关面板或屏幕下方既有提示区域，不产生瞬时不可读 Toast。

### 10.3 输入优先级

统一优先级：系统菜单 > 命轨/升阶/终局结算模态框 > 搜索或文本输入 > 库存/科技/建筑面板 > 世界建造与单位控制。按键按下与按钮点击都调用领域命令；测试必须通过真实 Input System 主循环覆盖选择命轨、打开详情和 `U` 升阶，不能只直接调用 presenter 或 runtime 方法。

## 11. 管理者修改器

修改器仅在 Development/Editor 开发许可下出现，沿用正式中文名称、列表查找和输入查找两种方式。新增动作：

- 设置或增减关注度；
- 选择三条命轨之一、设置命轨等级；
- 创建/读取/清除回溯锚点；
- 增加或偿还指定资源债务；
- 触发、完成或重置本会话压力遭遇夹具；
- 设置晶壳母体击败状态；
- 满足/清除四项升阶测试条件；
- 执行首次文明升阶；
- 查看关注度提交 ID、阈值锁存、遭遇队列和配置签名。

玩家看到的条目必须是“增加关注度”“解锁遗产解析”“触发晶壳母体”等游戏内名称，不能显示函数名。除明确标注的测试夹具恢复外，修改器必须调用与玩家相同的公共命令和校验，不直接写 UI 或私有字段。使用修改器的会话标记 `DeveloperModifierUsed=true`，验证记录不能当作自然流程证据。

## 12. 性能与稳定性

- 关注度和条件更新完全事件驱动，禁止 `Update` 中扫描全部建筑、科技或敌人。
- HUD 只在 progression revision 变化时重建快照；连续动画采样上限 10 Hz。
- 关注度历史固定 128 条，压力队列正式上限 3，命轨 offered 数固定 3；存档大小有确定上界。
- 阈值遭遇复用既有固定步长战斗循环、对象池和空间查询；Boss 占位不得引入逐帧分配。
- 无规则变化的稳定运行 300 个固定 tick 应产生 0 B GC Alloc；详情面板关闭时不格式化历史文本。
- 加载、回溯和升阶只能各发布一次 revision；不得因逐字段恢复造成 HUD 重建风暴。
- 配置和存档枚举按稳定 ID 排序，保证同输入、同 seed、同 tick 得到一致队列和结果。
