# WasteCity `IDEA-0016` 正式二维美术生产管线规格

**日期：** 2026-08-23

**关联需求：** `IDEA-0016`

**需求状态：** 已明确 / 已批准 / 未实现

**Unity：** `2022.3.62f1`

**目标场景：** `Assets/_Game/Scenes/GrayboxPrototype3D.unity`

> 本文只固定正式二维美术的内容、生产、导入、映射和验收边界。用户已经确认六个大类的基础风格，不等于任何正式批次已经生成、进入仓库、接入 Unity、通过自动化或完成人工验收。本文也不把预览图、本机生成缓存、程序化占位或第三方参考写成正式资产。

## 1. 目标与非目标

本管线要让 `IDEA-0016` 的资源、配方、43 个科技节点、30 个建筑定义、人物、UI 和世界标记获得可追溯、可替换、可回退的透明二维表现，并保证运行时只按正式稳定内容 ID 取图。它不新增玩法真值，不修改地图、seed、资源节点、建筑占地、研究前置、库存规则或 schema `31`。

本阶段明确不包含：

- 任何建筑、人物、资源节点的三维模型、动画、VFX 或 SFX；
- 重新设计现有地图、地形、矿点类型、位置或储量；
- 把科技预览文本冒充已经接入的玩法效果；
- 把 Development 修改器或场景 UI 作为图标映射真值；
- 下载、描摹或改色复制第三方游戏的具体图标、角色、建筑或 UI；
- 为极低概率且对当前可信本地开发流程没有现实影响的假设建立平行资产系统。

## 4. 逐项内容简介门

任何正式图片生成前，必须先在机器清单中为该项填写完整内容简介。简介由正式目录和 GDD 规则导出，不能只凭中文名称猜图。

每项必填：

1. `contentId`：玩法目录已有的稳定 ID；纯 UI/人物/标记使用经审核的新稳定 ID；
2. `displayNameZh`：游戏中的中文名；
3. `visualClass`：`item`、`ui`、`technology`、`building`、`character`、`world-marker` 之一；
4. `route`：`common`、`technology`、`cultivation`、`biological`、`psionics`；
5. `tier`：内容层级或 `0`；
6. `sourceSummaryZh`：物品来源、建筑取得方式或内容出现条件；
7. `useSummaryZh`：物品用途、科技作用、UI/标记使用位置；
8. `unlockSummaryZh`：研究、建筑或发现前置；无前置时明确写“默认”；
9. `loreBriefZh`：一至三句背景简介，说明世界观身份和形成原因；
10. `visualKeywordsZh`：主体、材料、形状、路线色、镜头和光影关键词；
11. `forbiddenElementsZh`：禁止误画、易混淆对象、不得烘焙的文字/状态；
12. `runtimeUsages`：资源栏、背包、配方、科技树、建造栏、详情、人物面板或世界浮标等实际位置；
13. `displaySizesPx`：所有实际显示尺寸，不能只写源图尺寸；
14. `safeArea`：主体或可拉伸区域的归一化安全区；
15. `fallbackKey`：缺图时使用的类别回退键；
16. `reviewState`：`brief-draft`、`brief-reviewed`、`art-ready`、`art-produced`、`imported`、`integrated`、`verified` 之一。

`reviewState` 未达到 `brief-reviewed` 时不得生成正式图；达到 `art-ready` 只表示图像生产资料齐全，不表示图已存在。`art-produced` 只表示源图和交付图完成离线检查；`imported`、`integrated`、`verified` 必须各有对应证据，不得越级。机器校验必须拒绝空简介、未知稳定 ID、未定义显示尺寸、缺失来源/用途的物品，以及岑烬身份字段不是男性遮脸的记录。

## 5. 稳定 ID 与视觉所有权

### 5.1 映射原则

- 资源、配方、科技和建筑继续使用各自正式目录的 `contentId`，不得为美术改名或建立同义玩法 ID；
- 视觉键采用三元组 `(visualClass, contentId, variant)`，默认 `variant` 为 `default`；
- 文件名只是交付名称，不是运行时查找依据；运行时必须从统一视觉目录解析三元组；
- 同一物品 Sprite 可被资源栏、背包、仓库、配方、生产详情、世界标记和修改器复用，不得由各 UI 维护平行字典；
- 配方必须有自己的视觉登记。若正式设计决定以“主产物图标 + 机器/手工角标”组合表达，组合规则仍由配方 `contentId` 的视觉条目持有，不能由按钮临时猜测；
- 世界标记框与中心物品图标是两个视觉层。标记框只映射标记内容 ID，中心层解析资源 `contentId` 的物品 Sprite；
- 正常、悬停、选中、锁定、不可用、枯竭、采集中等状态优先由运行时颜色、遮罩、角标或外部提示表达，不批量复制内容图。

### 5.2 计数合同

- 科技批次必须与 `ResearchCatalog.All` 的 **43** 个稳定 ID 一一对应；缺失、重复或额外科技图均阻断接入；
- 建筑批次必须与 `BuildingCatalog.All` 的 **30** 个稳定 ID 一一对应，其中包含普通建造目录的 28 项及两个升级目标；不得只为 `BuildMenu` 生成 28 张后把升级目标写成完成；
- 物品批次以完成目录统一后的正式资源总表为准，目标约 30–32 种，但开始批量生成前必须由清单冻结精确数量；
- 正式配方、UI、人物和世界标记的数量同样在内容清单冻结时精确记录，不在本文凭估计补数。

### 5.3 建议的稳定视觉键

纯表现内容采用可验证的稳定 ID，例如：

- `core.ui.frame.primary-panel`；
- `core.ui.icon.search`；
- `core.character.cen-jin`；
- `core.world-marker.resource-node`；
- `core.visual.fallback.item`、`core.visual.fallback.technology` 等六类回退键。

建议值不构成代码中已经存在的事实；实施时必须先经稳定 ID 测试和正式清单确认。既有内容以原 `contentId` 为映射目标，不把 `core.visual.*` 当作第二套资源、研究或建筑身份。

## 7. 图像规格、尺寸与安全区

| 大类 | 透明母版 | Unity 交付 | 主要实际显示 | 主体安全区 |
|---|---:|---:|---:|---|
| 物品 | `1024×1024` | `256×256` | `20/24/32/40/64 px` | 四边至少 12.5%，关键轮廓不得贴边 |
| 科技 | `1024×1024` | `256×256` | `32/48/64/80 px` | 四边至少 12.5%，核心原理占主体面积 55%–75% |
| 建筑 | `1024×1024` | `256×256` | `48/64/96 px` | 四边至少 10%，底部落点统一，最高点不越安全区 |
| 人物 | `2048×2048` | `512×512` | `96/128/192/256 px` | 头像/半身关键轮廓位于中央 80%，观察窗不得小于最小可读线宽 |
| 世界标记 | `1024×1216` | `256×304` | 标记 `64×76 px`，中心物品 `40–44 px` | 外框距边至少 6%；中央孔见第 9 节 |
| UI 图标 | `1024×1024` | `256×256` 或按组件清单 | `16/24/32/48/64 px` | 四边至少 12.5%，单色状态下也可辨识 |
| UI 九宫格 | 按组件，最小 `512×512` | 由清单给出，不任意缩放源文件 | 可从最小卡片拉伸到全屏面板 | 四角与边框均在不可拉伸区，中央为纯可拉伸区 |

所有尺寸均为合同而非已完成事实。若实际 UI 布局需要表外尺寸，先回写清单，再生成或导出；不得在不同界面偷偷保留多套同义图标。

### 7.1 缩小 QA

每张内容图必须自动生成透明、50% 灰、深色和浅色四种底板上的缩小联络表，并以最近实际用途检查。最低门：

- 物品在 `20 px` 仍能与同类相邻项凭轮廓或核心色块区分；
- 科技在 `32 px` 可识别核心原理，在 `48 px` 可与同层相邻节点区分；
- 建筑在 `64 px` 可识别主要功能轮廓和朝向，不依赖细管线或文字；
- UI 操作在 `16 px` 不糊成实心块；
- 人物在 `96 px` 保留岑烬的窄青色观察窗与长外套身份；
- 世界标记在 `64×76 px` 不遮住中心 `40–44 px` 物品图标和下方运行时文字；
- 缩小后不得出现绿边、白边、黑色脏边、单像素游离噪点或透明孔闭合。

视觉相似项先修改主体轮廓、负形和主色块，不用新增细字、细纹或粒子掩盖问题。

## 8. UI 九宫格与图集

工业指挥终端面板分为标题框、导航/筛选、内容卡、状态条、提示、确认和弹出层。所有需要任意拉伸的边框必须使用 Unity Sprite `Border` 和 9-slice：

- 四角、机械接头和端帽全部位于不可拉伸区；
- 上下边只允许横向拉伸，左右边只允许纵向拉伸；
- 中央区保持低噪声，不能烘焙文字、图标、路线色或方向性光影；
- `Image.Type` 使用 `Sliced`，不得用 `Simple` 拉扁角件；
- 最小显示尺寸不得小于左右/上下 Border 总和；
- Border 像素值写入机器清单，并由 Editor 测试核对 `.meta`；
- 圆角、边框厚度和可点击范围是不同概念，透明圆角不能缩小正式 Raycast 区域；
- 常态、悬停、按下、选中、禁用由 ColorBlock、覆盖层或状态 Sprite 组合，不为每个面板复制完整底图。

UI、物品、科技、建筑和世界标记分别进入用途明确的 SpriteAtlas；人物可按实际内存测试决定独立打包。Atlas 不能改变稳定视觉映射，不能依赖打包顺序，且 Release 和 Development 的内容一致，修改器专用图不得进入 Release 引用链。

## 9. 世界资源标记合同

`core.world-marker.resource-node` 使用“极简战术准星”外框。Unity 交付图 `256×304` 的中央必须有至少 `176×176 px` 的全透明矩形孔，对应运行时 `44×44 px`；如最终显示中心图标采用 `40×40 px`，仍保留该孔而不缩小。

硬性规则：

- 中央孔内 Alpha 必须逐像素为 `0`，不能只有视觉上透明的低 Alpha；
- 框图不得包含铁矿、能晶、石料、生物质、水或后续材料图；
- 中文资源名与剩余储量由下方独立运行时文本显示；
- 正常、枯竭、采集中、兼容节点和合法锚点使用运行时染色、角标或外部高亮，不烘焙为平行框图；
- 中心物品 Sprite 必须复用物品视觉目录映射；未知或缺失资源使用物品类回退，不让整个标记消失；
- 外框和中心图标共同面向相机，但不拥有节点位置、储量、枯竭或放置合法性真值；
- 运行时复用既有标记对象，不因状态、储量文本或资源图变化逐帧创建 Sprite、材质或 GameObject。

自动 Alpha 检查至少覆盖四角透明、中央 `176×176` 全透明、边界无绿色溢色，以及缩小后中心孔仍开放。

## 10. 人物与建筑专项合同

### 10.1 岑烬

岑烬的正式内容 ID 由人物清单固定，并映射到唯一正式人物图。简介和图像必须同时满足：男性、遮脸、修长维修指挥者、窄青色观察窗、长维修外套、前臂终端、受控尺寸维修工具。禁止写实/半写实、女性、露脸、重装士兵、巨型工具、过多零碎挂件或借武器遮掩职业身份。

任何一项身份校验不符都退回生产，不允许靠文件名“CenJin”或说明文字掩盖画面错误。人物风格批准不代表岑烬正式头像或立绘已经生成。

### 10.2 30 个建筑定义

每张建筑图使用相同 elevated 3/4 相机、地面落点、视野占比和主光方向。占地较大的建筑可以缩小主体，但不得裁切；相同占地的建筑保持可比较体量。输入口、处理核心、输出口只通过结构方向和有限状态灯表达，不烘焙配方、资源文字或产量。

30 张必须逐 ID 对齐 `BuildingCatalog.All`。普通目录和两个升级目标共享风格但保持轮廓差异；升级目标不可用简单改色代替。尚无正式三维模型不阻止二维建筑图生产，但不得把二维图写成三维模型已完成。

## 11. Unity 导入策略

由 Editor 导入规则只作用于 `Assets/_Game/Art/Production2D/`，不得修改地形或其他既有贴图导入规则。

通用设置：

- `Texture Type = Sprite (2D and UI)`、`Sprite Mode = Single`；需要同图多 Sprite 时必须在清单显式批准；
- `Alpha Source = Input Texture Alpha`、启用透明 Alpha，禁止以白底或色键图直接接入；
- `sRGB = true`、`Wrap Mode = Clamp`、`Mip Maps = false`；
- `Filter Mode = Bilinear`；若小尺寸 QA 证明某一类需要 Point，按整个类统一并记录，不逐图随意设置；
- `Sprite Mesh Type = Full Rect`，以保证 UGUI、9-slice、中央孔和安全区稳定；
- Pivot 默认 `(0.5, 0.5)`；建筑如需统一底部落点，只能使用清单固定的同类 Pivot，不按单图目测漂移；
- `Pixels Per Unit` 统一由类级导入配置给出，不参与 UI 实际像素尺寸真值；
- 不使用 Crunch。默认桌面压缩和 Atlas 格式须经 Alpha 边缘与显存对比后一次性冻结；在冻结前不得宣称最终显存预算已通过；
- UI 9-slice 的 Border、世界标记孔尺寸和 Sprite GUID 由 Editor 测试读取验证；
- `.meta` 必须随 PNG 一起提交，GUID 变化视为映射风险并阻断批量接入。

导入器只负责图片格式和 Sprite 元数据，不生成中文名、路线、解锁、来源用途或运行时状态，也不自动修改场景与 Prefab。

## 12. 正式批次顺序

正式生产采用可停止的批次，上一批通过内容、透明度、尺寸和缩小门后才进入下一批：

1. **管线黄金样板**：每类各 1 项，建立清单、导出、Alpha、导入、映射、回退和 QA 全链；
2. **物品基础批次**：先覆盖现有 15 种资源及所有当前 UI 用法，再覆盖目录统一后新增资源；
3. **生产与配方批次**：所有正式机器/手工配方视觉登记，接入合成、生产详情和修改器；
4. **科技批次**：按稳定 ID 一次冻结 43 项内容简介，按路线/层级分小批生产，最终以全树联络表验收；
5. **建筑批次**：按基础/生产/物流/防御/四路线分组完成 30 项，最终以统一 `64 px` 联络表验收；
6. **UI 批次**：面板、9-slice、分类、路线、状态、操作与搜索图标；先树和资源闭环所需组件，后补辅助界面；
7. **人物批次**：先岑烬黄金正式图，再处理本阶段清单中经批准的其他人物；
8. **世界标记批次**：极简准星框、必要外部状态提示和中心复用接线；
9. **全局协调批次**：四路线色、同义符号、相邻项区分、Atlas、默认 3D 场景和三项构建复验。

允许不同类别在文件层面并行生产，但同一清单、Atlas、导入规则或 Unity 映射资产不得由多个任务同时修改。任何批次发现内容语义或稳定 ID 冲突时停止该项，不能让美术自行改玩法目录。

## 13. 机器清单

正式清单建议为 UTF-8 JSON：

`Docs/Engineering/idea-0016-visual-assets.json`

顶层字段：

| 字段 | 含义 |
|---|---|
| `schemaVersion` | 美术清单自身版本，不是游戏存档 schema |
| `ideaId` | 固定 `IDEA-0016` |
| `unityVersion` | 固定 `2022.3.62f1` |
| `generatedAtUtc` | 生成或复核时间；不得被运行时使用 |
| `catalogFingerprint` | 参与内容目录稳定 ID 和关键字段的确定性摘要 |
| `selectedStyleIds` | 六类已确认风格键 |
| `entries` | 按 `visualClass/contentId/variant` 排序的正式条目 |

每个 `entries[]` 至少包含：

| 字段 | 约束 |
|---|---|
| `visualEntryId` | 全清单唯一、符合 StableId 格式 |
| `visualClass` | 六类枚举之一 |
| `contentId` | 对应正式内容 ID；必须能由所属目录解析 |
| `variant` | 默认 `default`；非默认变体需说明不可由运行时状态合成的原因 |
| `displayNameZh` | 正式中文名 |
| `route` / `tier` | 路线与层级 |
| `sourceSummaryZh` / `useSummaryZh` / `unlockSummaryZh` | 来源、用途、解锁 |
| `loreBriefZh` | 背景简介 |
| `visualKeywordsZh` / `forbiddenElementsZh` | 生成与审核约束 |
| `runtimeUsages` / `displaySizesPx` | 使用位置和实际尺寸 |
| `sourceAssetPath` | `Docs/Art/IDEA-0016/Source/...` 项目相对路径 |
| `unitySpritePath` | `Assets/_Game/Art/Production2D/...` 项目相对路径 |
| `unityGuid` | 接入后写入；未接入时必须为空且状态不能超过 `art-ready` |
| `pixelWidth` / `pixelHeight` | Unity 交付尺寸 |
| `safeAreaNormalized` | `x/y/width/height` |

| `centralTransparentRectPx` | 世界标记中央孔；其他类为空 |
| `fallbackKey` | 类别正式回退键 |
| `promptSummaryZh` | 生成/制作方法的非敏感摘要 |
| `toolAndModel` | 制作工具与版本；手绘时记录工具 |

| `reviewEvidence` | 自动化、截图和用户结论分别记录，不混写 |

## 14. 回退策略

统一视觉目录按以下顺序解析：

1. 精确 `(visualClass, contentId, variant)`；
2. 同内容的 `default`；
3. 对应 `fallbackKey` 的类别正式回退；
4. 现有清楚可替换的程序化占位，仅作为最后开发回退。

未知资源、旧存档保留的缺失内容或未完成正式图不得抛异常、显示空白透明点击区或阻断保存/加载。回退必须保留类别和路线基本识别，并在 Development/Editor 记录一次性可定位告警；Release 不刷屏。回退不授予科技、配方、建筑或资源效果，也不把缺失内容改成另一个已知 ID。

关闭 `IDEA-0016` 正式视觉目录后，现有灰盒/占位主循环必须仍可运行。单项图失败只移除其映射并回到类别回退，不删除玩法组件或重写场景。

## 15. Git LFS 与来源完整性

仓库当前 `.gitattributes` 已将 `*.png`、`*.psd`、`*.kra`、`*.ora` 等正式二进制格式交给 Git LFS。首张正式图提交前和每个批次暂存后必须验证：

- `git check-attr filter diff merge text -- <path>` 返回 LFS 属性；
- `git lfs ls-files` 覆盖所有新增二进制源和交付图；
- Git 索引中的二进制文件内容是以 `version https://git-lfs.github.com/spec/v1` 开头的真实 LFS pointer；
- 工作树文件能被图像解码器读取，不能把 pointer 文本当作 PNG/PSD；
- `git lfs fsck` 通过，并在普通 push 后确认 LFS 对象上传成功；
- `.meta`、JSON、Markdown 保持普通文本，不通过 LFS；
- 新机器或干净 clone 的验收先完成 `git lfs pull` 和文件签名/尺寸检查。

任何对象缺失、指针被当图片、普通 Git blob 误入或许可证不明都阻断该批提交；不得通过取消 LFS 规则绕过。

## 16. 质量目录与推荐复用边界

实施时新增的生产代码、Editor 导入/生成器、机器清单、Unity 视觉目录、SpriteAtlas、场景接线和测试必须进入 `Docs/Engineering/project-quality-catalog.json` 的 `IDEA-0016` 功能组。至少建立以下责任边界：

- **内容简介/机器清单校验器（Editor）**：验证字段、ID、计数、路径、尺寸、Alpha、摘要和目录引用；不拥有玩法内容；
- **统一二维视觉目录（推荐复用）**：只按稳定视觉键解析 Sprite、9-slice 元数据和回退；不拥有中文名、资源数值、研究状态或 UI 布局；
- **类级导入规则（Editor）**：只管理指定目录的 TextureImporter；不扫描或修改地形和其他美术；
- **联络表与缩小 QA 生成器（Editor）**：产生只读证据；不改变源图或自动宣称视觉通过；
- **正式 3D 表现适配**：消费统一目录并组合状态；不复制稳定 ID 映射或玩法判断。

上述公共能力完成后更新 `Docs/09-Reusable-Project-Catalog-ZH.md`，说明“能解决什么、在哪里、怎么复用、不能负责什么、改后跑哪组测试”。只服务单一场景布局的适配器标为“仅限场景”，不得包装成通用玩法服务。

## 17. 测试与验收门

### 17.1 先红后绿的自动化

实现前先写失败测试，至少覆盖：

1. 清单 schema、排序、唯一键、StableId、项目相对路径和必填简介；
2. 正式资源、配方、43 科技和 30 建筑目录引用完整，无重复、遗漏或幽灵条目；
3. 每种物品有来源、用途、显示尺寸、正式图或类别回退；
4. 岑烬人物记录为男性、遮脸且禁用项完整；
5. PNG 可解码、尺寸/Alpha/安全区正确，源图和交付图 SHA-256 匹配清单；
6. 世界标记中央 `176×176 px` 全透明、无烘焙文字/矿物的人工复核证据字段齐全；
7. UI 9-slice Border 与清单一致，中央拉伸后角件不变形；
8. TextureImporter、Sprite GUID、Pivot、Atlas 和视觉目录确定性；
9. 精确映射、默认变体、类别回退和未知稳定 ID 回退；
10. 资源栏、背包、仓库、合成、生产详情、科技树、建造栏、人物面板、世界标记和 Development 修改器均消费统一目录；
11. 科技树拖动、缩放、搜索、筛选和打开自动定位时图标与监听器稳定，真实 Input System 不穿透；
12. 世界标记状态切换和储量变化不逐帧创建 Sprite、材质、字符串或 GameObject；
13. schema `31` 新旧内容往返不因图片缺失而丢失、改名、复制资源或错误解锁科技；
14. Release 无 Development 修改器入口或专属图引用。

### 17.2 视觉和性能证据

- 每批保存原尺寸、缩小联络表、Alpha 检查图和默认 3D 场景截图；
- 43 科技以全树及各缩放级别检查节点、路线、前置连线和相邻图标区分；
- 约 30–32 种物品以资源栏最小尺寸、背包、仓库和配方四种上下文检查；
- 30 建筑以统一 `64 px` 联络表和正式建造栏/目录检查；
- 世界标记在密集节点区检查遮挡、中心图、中文名和储量，不以单个空白场景代替；
- 混合场景验证不得出现逐帧全量目录重建、监听器累积、材质实例化、无界对象增长或持续托管分配；
- Atlas、纹理常驻内存、Draw Call、GPU/显存和 Windows 视觉结果记录真实硬件数据，不能由静态测试推断。

### 17.3 完成门

按风险依次运行聚焦 EditMode、聚焦真实输入 PlayMode、日常完整 EditMode、完整 PlayMode和项目质量门；随后完成 Windows Release 3D、Windows Development 3D、macOS universal 3D 三项现役构建，运行官方文档生成、验证和 `RecordVerification`。只有触及地形源、地形导入规则、Texture2DArray Builder、数组生成或准备发布时才运行 `TerrainAssetDeep`；本二维目录默认不触发它。

用户对六类风格的选择可以记录为“风格已确认”；正式资产的逐批视觉判断、完整试玩和真实 Windows 10/11 视觉/GPU/显存/内存结论只能依据实际结果。自动化、macOS 构建、预览图或本文均不得把这些状态提前写为“已验证”。

## 18. 停止条件

出现以下任一情况即停止相关批次并报告：

- 正式目录数量或稳定 ID 与清单不一致；
- 必须修改地图、seed、建筑占地、研究含义或 schema `31` 才能继续；
- 来源/许可证不清楚，或候选/未入选参考混入正式目录；
- LFS 对象缺失、索引不是 pointer、工作树是 pointer 文本或 GUID 意外改变；
- 正式图不能在批准实际尺寸辨认，世界标记中央孔闭合，或 9-slice 必然变形；
- 新文件无法纳入质量目录或公共映射需要复制玩法真值；
- 计划外生产文件、Build Settings、ProjectSettings、地形导入规则或其他受保护资产发生变化。

除上述真实边界外，相似的小型图像清理、统一边距、受控线宽和批次内命名调整可依本规格自主完成，不为对当前本地可信制作流程无现实影响的极低概率情形扩大系统。
