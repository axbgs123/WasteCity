# 用户反馈与变更控制文档设计

> 日期：2026-08-04
> 状态：已获用户确认
> 适用项目：《废土移动城市》

## 1. 目标

建立一份所有开发者和 AI 开发代理在开始工作前必须阅读的动态补充文档，用于：

1. 记录用户试玩或测试时发现的 Bug；
2. 记录用户提出的新构思；
3. 申请修改主 GDD、正式路线图或其他现有文档；
4. 分别标记一项内容是否已经获得批准、是否已经实现及是否完成验证；
5. 通过 Git 提交和 GitHub 分支保留完整变更历史。

该文档是用户输入的统一入口，但登记本身不等于批准，也不自动覆盖主 GDD、路线图或已经运行的代码事实。

## 2. 文件与入口

新增主文档：

`Docs/06-User-Feedback-and-Change-Control-ZH.md`

新增仓库级开发规则：

`AGENTS.md`

同时修改：

- `README.md`：在文档优先级和开发入口中加入补充文档；
- `Docs/00-README-ZH.md`：将补充文档列为每次开发启动前的必读文件。

`AGENTS.md` 负责要求所有进入仓库的开发者或 AI 代理在分析、设计或修改代码前读取补充文档。补充文档负责保存用户输入、决策和实现状态。

## 3. 权威边界

补充文档中的记录采用“先登记，确认后生效”：

- `待确认`：只代表用户提出或测试发现，不得据此修改正式需求或扩大开发范围；
- `已批准`：允许进入设计、计划和实现流程；
- `已拒绝`：保留历史，不进入开发；
- `已撤回`：用户取消，保留撤回原因。

只有审批状态为 `已批准` 的记录才能改变正式文档或进入开发。修改原文档时，必须在原文档和补充记录之间留下双向引用。

运行代码、自动化测试和构建结果仍代表“当前已经实现的事实”。补充文档不能把计划内容描述成已经实现。

## 4. 双状态模型

每条记录必须同时包含两个互不替代的状态。

### 4.1 审批状态

- `待确认`
- `已批准`
- `已拒绝`
- `已撤回`

### 4.2 实现状态

- `未实现`
- `开发中`
- `已实现待验证`
- `已验证`
- `不适用`

规则：

- 新记录默认是 `待确认 + 未实现`；
- 纯文档讨论在尚未修改原文档前仍为 `未实现`；
- 代码或文档修改完成但未通过规定检查时为 `已实现待验证`；
- 只有对应测试、文档检查或人工验收完成后才能标记 `已验证`；
- 被拒绝或撤回的记录，实现状态通常保持 `未实现`；
- 仅用于澄清、无需产生修改的记录可标记为 `不适用`。

## 5. 记录类型与稳定 ID

使用三类稳定 ID：

- Bug：`BUG-0001`
- 新构思：`IDEA-0001`
- 文档变更：`DOC-0001`

编号在各类型内单调递增，已关闭、拒绝或撤回的编号不得复用。

每条记录至少包含：

- ID；
- 提出日期；
- 类型；
- 标题；
- 用户原始描述；
- 复现步骤或设计动机；
- 预期结果；
- 实际结果（Bug 必填）；
- 审批状态；
- 实现状态；
- 优先级；
- 影响范围；
- 关联正式文档；
- 关联提交；
- 验证证据；
- 最近更新时间；
- 备注或决策原因。

## 6. 文档结构

主文档包含：

1. 开发前必读声明；
2. 使用规则与状态定义；
3. 当前待处理总表；
4. Bug 详细记录；
5. 新构思详细记录；
6. 文档变更详细记录；
7. 已关闭记录；
8. 更新模板；
9. GitHub 同步规则。

总表只保留定位和决策所需的关键字段，详细信息写入对应记录章节，避免表格过宽且难以维护。

## 7. 更新流程

### 7.1 用户提出内容

1. 先原样保留用户意图；
2. 分配稳定 ID；
3. 默认登记为 `待确认 + 未实现`；
4. 补充必要的复现信息、影响范围或关联文档；
5. 单独提交并推送 GitHub。

### 7.2 用户批准

1. 将审批状态更新为 `已批准`；
2. 明确验收条件；
3. 如果涉及修改原文档，先更新对应正式文档并建立双向引用；
4. 进入正常的设计、计划、测试先行和实现流程。

### 7.3 开发与验证

1. 开始开发时标记 `开发中`；
2. 实现提交完成后标记 `已实现待验证` 并填写提交哈希；
3. 通过对应自动化测试、构建或人工验收后标记 `已验证`；
4. 更新补充文档并再次推送 GitHub。

每次状态变化必须记录日期和证据，禁止直接从 `未实现` 跳到 `已验证` 而不填写实现提交及验证依据。

## 8. GitHub 同步规则

- 补充文档及其入口规则必须纳入 Git；
- 每次新增记录、批准、实现或验证都形成独立提交；
- 更新后推送当前开发分支，不强制推送；
- 未经用户明确授权，不自动合并默认分支、不创建公开 Release；
- 本机缓存、账号凭据、Unity 许可证和绝对路径不得进入提交；
- GitHub 暂时不可用时可先本地提交，恢复连接后按原顺序推送，不改写历史。

这里的“实时更新”指：每次用户明确新增或改变记录后，在同一工作流程内完成文档修改、提交和 GitHub 推送，而不是后台持续同步或绕过 Git 审核。

## 9. 开发者必读门

任何开发者或 AI 代理开始任务前必须：

1. 阅读 `AGENTS.md`；
2. 阅读 `Docs/06-User-Feedback-and-Change-Control-ZH.md`；
3. 检查是否存在与当前任务相关的 `已批准`、`开发中` 或 `已实现待验证` 记录；
4. 在计划中引用相关稳定 ID；
5. 不得实现仍为 `待确认` 的新构思或文档变更；
6. 完成后回写实现状态、提交哈希和验证证据。

若补充文档与正式文档冲突：

- `已批准` 的文档变更记录要求先更新正式文档，再按正式文档开发；
- 尚未更新正式文档前，不得自行解释冲突；
- Bug 记录可以证明当前实现存在问题，但修复范围仍以批准内容和验收条件为准。

## 10. 验证

接入完成后必须验证：

- 根目录存在 `AGENTS.md`，且明确要求阅读补充文档；
- README 和交接说明均能找到补充文档；
- 补充文档包含三类模板、双状态字段及实现标记；
- 文档中没有未解释的 `TBD`、`TODO` 或含糊状态；
- `git diff --check` 通过；
- 提交中不包含本机 Unity 离线包配置或生成缓存；
- GitHub 远端分支提交哈希与本地一致。

## 11. 非目标

本次不创建：

- 自动后台同步服务；
- GitHub Issue 自动化机器人；
- Web 表单或独立反馈网站；
- 自动批准或自动修改主 GDD 的流程；
- 绕过用户确认的需求实现机制。
